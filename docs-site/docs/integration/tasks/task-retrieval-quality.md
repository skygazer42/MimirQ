# 任务：检索效果变差

**本文适用于**：**数据 Owner、算法/平台工程师、集成方**；业务反馈「问不到、答不对、变慢」时，把问题从 **体感** 收敛到 **可改项**。

## 业务目标

- 区分 **无结果、弱相关、模型胡编、延迟** 四类体验，避免一律归因「模型不行」。  
- 明确当前 **检索配置**（模式、重排、融合、模板）与 **数据质量**（切块、索引、权限过滤）各自责任。  
- 产出可跟进的 **变更项**（调参、重建索引、补数据、修权限）。

## 前置条件

- 有可复现的 **用户问题示例** 与 **预期应命中的文档/段落**（内部可脱敏）。  
- 可访问 **检索调试/解释** 类产品能力或 API（以部署为准；仓库有 retrieval 相关 guides）。  
- 已确认 **数据集 RAG 默认** 与对话时是否覆盖（见 [数据集上线](./task-dataset-go-live.md)）。

## 推荐步骤（概要）

1. **复现**：同一问题固定 `dataset_id`、模板、用户身份，排除「问错库」。  
2. **召回层**：查是否 **过滤过严**（权限、状态、时间）、**切块** 是否切碎/合并不当。  
3. **排序层**：看重排/融合是否启用、参数是否与文档类型匹配（见仓库 [retrieval 相关 guides](https://github.com/skygazer42/MimirQ/tree/main/docs/guides)）。  
4. **生成层**：若召回正确但答案偏，记录 prompt 模板与 **温度/约束** 变更窗口。  
5. **记录**：为每条问题保留 **trace / explain 摘要**（注意 PII），便于回归。

## 验收标准（业务）

- [ ] 对抽样问题，**命中率或满意度** 相对基线可量化对比（即便只是「前后盲评」表）。  
- [ ] 已列出 **下一步负责人**（数据/平台/模型）与 **截止时间**。  
- [ ] 若需重建索引或全量重嵌入，已有 **变更窗口与回滚** 说明。

## 失败时的业务影响与止损

| 现象 | 业务影响 | 止损动作 |
| --- | --- | --- |
| 全库无结果 | 对话产品不可用 | 查索引服务与 embedding 任务；临时切换备用检索模式（若支持） |
| 仅某数据集差 | 单客户投诉 | 隔离该数据集的 rag_defaults；回滚最近策略变更 |
| 延迟飙升 | 体验崩塌 | 查向量与 DB 负载；限流与缓存；[可观测性](../patterns/observability-requests.md) |
