# 任务：治理与隔离审批

**本文适用于**：**合规、安全、数据 Owner、运营审核**；在 **敏感内容、违规片段、隔离区** 流程中，保证 **可审计、可放行/可拒绝**，且不误伤正常业务。

## 业务目标

- **策略可见**：哪些内容进入隔离、谁有权审核、审核 SLA 是多少。  
- **动作可追溯**：每条放行/拒绝可在审计日志或工单中对齐到 **人与原因**。  
- **与问答一致**：被隔离内容 **不应** 在未放行前进入对外答案（或明确产品例外并备案）。

## 前置条件

- 组织已定义 **敏感分级** 与 **治理开关**（上传时 `governance_*` 等字段，见 OpenAPI upload body）。  
- Web **隔离区/审核** 路由对审核员可用（见 Frontend [文档 — 用户路径](../../frontend/documents/overview.md) 中 quarantine 等）。  
- 法务/安全已确认 **留存周期与导出** 要求。

## 推荐步骤（概要）

1. **对齐策略**：与产品确认 **默认严格度**（宁可多进隔离 vs 宁可少打扰）。  
2. **抽检**：从隔离队列抽样，核对 **命中原因** 与 **原文片段** 是否合理。  
3. **审批**：按角色 **放行/拒绝**；拒绝需带 **可理解原因** 给上游（运营/用户）。  
4. **回归**：放行后抽样 **对话/检索**，确认内容按预期进入或仍被排除。  
5. **审计导出**：按合规要求导出 **一段时间内的决策记录**（接口以 OpenAPI governance/audit 为准）。

## 验收标准（业务）

- [ ] 审核队列 **无不明原因积压**；超时有人兜底。  
- [ ] 随机抽查 **问答结果** 不包含未放行敏感片段（在定义的威胁模型内）。  
- [ ] **变更**（策略 JSON、规则版本）有登记并可回滚。

## 失败时的业务影响与止损

| 现象 | 业务影响 | 止损动作 |
| --- | --- | --- |
| 队列爆炸 | 审核人力崩溃 | 临时放宽非关键类规则 + 分批；加急人力 |
| 误杀正常内容 | 业务停摆、投诉 | 快速放行通道；回滚最近规则版本 |
| 漏审敏感 | 合规风险 | 紧急下线相关文档；全量扫描同类模式 |
