# 任务：解析失败止损

**本文适用于**：**运维、集成工程师、数据 Owner**；当出现 **大量文档卡住、解析错误飙升、队列堆积** 时需要快速恢复业务可用性。

## 业务目标

- **缩短 MTTR**：区分是 **配置/解析器/依赖/单文件质量** 哪一类问题。  
- **控制影响面**：避免「坏一批配置」拖垮全租户文档处理。  
- **对用户可解释**：客服能回答「预计何时恢复、是否需重新上传」。

## 前置条件

- 可访问 **后端日志** 与 **文档状态/timeline API**（见 OpenAPI documents）。  
- 已知当前 **默认 parser_backend** 与可选后端列表（与部署一致）。  
- 若有 **解析工作台** Web 路由，确认值班人员有权访问（见 Frontend [文档 — 用户路径](../../frontend/documents/overview.md)）。

## 推荐步骤（概要）

1. **量化**：统计 `processing` 超时比例、失败 error 分布、是否集中在某数据集/某后缀。  
2. **单条深潜**：对一条失败文档 `GET .../status` + `GET .../timeline`（或等价），对齐后端日志 `request_id`。  
3. **依赖**：确认解析器侧车/外部 OCR/对象存储 **健康**；非 MimirQ 单点问题先切流或降级。  
4. **配置**：若确认为某 `parser_backend` 缺陷，在数据集或上传层 **临时切换默认后端** 并公告。  
5. **重试**：对可恢复类失败使用 `retry` / 批量 retry；对不可恢复类 **隔离** 并通知上传方换格式。

## 验收标准（业务）

- [ ] **新增文档** 恢复可在 SLA 内到达完成态，或明确 **失败原因** 展示给运营。  
- [ ] 根因已写入 **值班记录或工单**（配置版本、依赖版本、影响数据集列表）。  
- [ ] 若需代码/配置变更，已有 **回滚点**（上一版镜像或配置导出）。

## 失败时的业务影响与止损

| 现象 | 业务影响 | 止损动作 |
| --- | --- | --- |
| 全队列堵死 | 全租户无法更新知识 | 暂停批量入口；扩容 worker；临时提高并发上限（评估风险） |
| 单类型文件全挂 | 某业务线无法入库 | 对该 MIME 走人工通道或换解析器 |
| 间歇 503 | 体验差、重试风暴 | 退避与熔断；[错误码与重试](../patterns/idempotency-retries.md) |
