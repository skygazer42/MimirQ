# Pipeline Plugins

Pipeline plugins are registered plugin packages for governance, chunking, and KG
extraction. MimirQ owns the registration, validation, execution, and indexing
contracts; domain-specific rules live in plugin package files so they can be
added without changing the backend application code.

## Contract

Each plugin package lives under a configured plugin directory, default:

```text
plugins/pipelines/<plugin-name>/
```

Required files:

```text
mimirq-plugin.json
plugin.py
.mimirq-plugin-test.json
```

Recommended contract files:

```text
metadata_schema.json
retrieval_text_schema.json
retrieval_policy.json
golden_rules.json
sample.json
README.md
```

One business package should normally be one plugin. For example, a complex
business knowledge package can have internal handlers for catalog records,
guided workflows, FAQs, regulations, and tables, but it should still be one
plugin package. Do not create one plugin per region or per file type unless the
business boundary is actually different.

The test report is generated by the local runner. The API only marks a plugin as
executable when:

- `mimirq-plugin.json` has `status: "published"`.
- `.mimirq-plugin-test.json` exists.
- The report `plugin_id` and `version` match the current manifest.
- The report `package_hash` matches the current plugin package files. The hash
  covers manifest, Python source, declared contracts, samples, and local
  resource files such as `synonyms.json`; generated files such as
  `.mimirq-plugin-test.json`, hidden files, `__pycache__`, and `.pyc` are ignored.
  Pure documentation files such as `README.md`, `LICENSE`, and `CHANGELOG.md`
  are also ignored so docs edits do not disable a tested plugin.
- Every declared stage has a passing test entry.
- Metadata contract validation passes for every declared test stage.

If the script or resource files change after testing, the plugin becomes stale and cannot be
selected/executed until the runner is executed again.

## Manifest

```json
{
  "id": "domain-knowledge-demo",
  "version": "1.0.0",
  "name": "领域知识治理示例",
  "description": "按领域记录治理并切块知识包",
  "status": "published",
  "metadata_schema": "metadata_schema.json",
  "retrieval_text_schema": "retrieval_text_schema.json",
  "retrieval_policy": "retrieval_policy.json",
  "golden_rules": "golden_rules.json",
  "processing_templates": "processing_templates.json",
  "suggested_pipeline_patch": {
    "governance_enabled": true,
    "persist_parsed_content": true,
    "chunk_python_params": {
      "record_window_chars": 1500
    }
  },
  "entry": {
    "governance": "plugin.py:govern_documents",
    "chunk": "plugin.py:chunk_documents",
    "kg": "kg_builder.py:build_kg_events"
  }
}
```

Manifest top-level fields are a closed platform contract. Do not add business-specific top-level fields such as region, domain, record type, or custom limits. Put business fields in `metadata_schema.json`, behavior in plugin code, and small runtime knobs under `governance_python_params`, `chunk_python_params`, or `kg_python_params`.
Contract file fields must be non-empty relative paths when present:
`metadata_schema`, `retrieval_text_schema`, `retrieval_policy`, `golden_rules`, and
`processing_templates` either point to a local JSON file or are omitted
entirely.
Contract file fields must be strings; non-string values are rejected before file
resolution.
Contract JSON top-level fields are closed platform contracts.
Do not add business-specific top-level fields to `metadata_schema.json`, `retrieval_text_schema.json`, `retrieval_policy.json`, `golden_rules.json`, or `processing_templates.json`; put business metadata under `metadata_schema.fields`, retrieval composition under `retrieval_text_schema.stages`, retrieval strategy hints under `retrieval_policy`, evaluation declarations under the supported Golden rule arrays/templates, and operator-facing business template provenance under `processing_templates.templates`.
`processing_templates.json` is a plugin-owned template provenance contract:
MimirQ validates and exposes the declared `templates[]`, but does not copy those
business templates into platform built-ins.
`processing_templates.templates[].key` is plugin-local. Namespace business
template keys (for example with the plugin id or domain prefix) when they mirror
platform built-in template ideas, so UI and audit logs do not confuse plugin
provenance with platform built-ins. Plugin processing template keys must not collide with platform built-in processing script keys; if a plugin customizes a built-in idea, publish it under a plugin-owned key.
`processing_templates.templates[].implemented_by` must be a plugin-local symbol ref such as `plugin.py:chunk_documents` or `local_helper.py:normalize_rows`.
`processing_templates.templates[].related_implementations[]` must also be plugin-local.
The referenced symbol must exist in that plugin file. Function, class, and top-level assignment symbols are accepted so a template can point to either executable helpers or plugin-owned constants such as regex rules.
Do not point processing template provenance at `app.*`, `scripts.*`, or other
MimirQ platform modules; if a template needs business behavior, ship that
implementation inside the plugin package.

`suggested_pipeline_patch` is first validated as a partial `DocumentPipelineOptions`
object; unknown top-level keys are rejected, then it is exported through the narrower `PipelinePluginSuggestedPatch` API schema.
Allowed manifest suggestion fields are `governance_enabled`, `persist_parsed_content`, `governance_python_params`, `chunk_python_params`, and `kg_python_params`.
It must not set platform strategy fields.
Examples include `chunk_size`, `chunk_overlap`, `chunk_merge_small_min_chars`, or `chunk_strategy_params`, and it must not set built-in `governance_*` knobs other
than `governance_enabled`. Keep business-specific knobs inside
`governance_python_params`, `chunk_python_params`, or `kg_python_params` so the platform stores and
passes them through without learning their meaning. It must not set `governance_python_plugin`, `chunk_python_plugin`, or `kg_python_plugin`; activation refs come only from plugin manifest `refs`, and runners must not derive missing stage refs from another stage.
`governance_python_params`, `chunk_python_params`, and `kg_python_params` may be
suggested only when the plugin manifest declares the matching `governance`,
`chunk`, or `kg` entry stage.
`governance_python_params`, `chunk_python_params`, and `kg_python_params` may be suggested only for small primitive plugin knobs. All three python params objects are limited to small JSON primitive values; put larger or nested business configuration in the plugin package files instead of platform pipeline state.
`kg_python_plugin` registered refs must target the `kg` stage; do not pass a
`governance` or `chunk` ref to KG extraction.
At runtime, registered plugin refs must target the same stage as the API field
or runner function that uses them: `governance_python_plugin` uses
`:governance`, `chunk_python_plugin` uses `:chunk`, and `kg_python_plugin` uses
`:kg`.
Legacy Python import refs are disabled by default. Prefer registered
`plugin:<id>@<version>:<stage>` refs; only enable import refs by explicitly
setting `PYTHON_PIPELINE_PLUGIN_ALLOW_PREFIXES` for a trusted internal
migration path.

Entry targets must be strings. Entry modules must resolve inside the plugin directory.
Use local file targets such as `plugin.py:chunk_documents` or local module
targets such as `plugin:chunk_documents`.
Do not point entries at `app.*` platform modules; if a business needs special
behavior, ship it in the plugin package.
Entry callable names must be single Python identifiers such as
`chunk_documents`; dotted names, empty names, or expression-like targets are
rejected at manifest load time.
Do not use platform top-level names such as `app/`, `scripts/`, or `tests/` for
plugin entry files or import modules.
Plugin Python source files must not import MimirQ platform modules such as `app.*`, `scripts.*`, or `tests.*`, and must not place helper source under platform-shaped top-level directories such as `app/`, `scripts/`, or `tests/`.
Use plugin-local helpers or stable third-party dependencies instead, so business
plugins remain portable and do not depend on platform internals.
Entry stages are limited to `governance`, `chunk`, and `kg`; business-specific
sub-stages belong inside plugin code and metadata, not the platform manifest.

Governance and chunk stage functions receive documents and return
`langchain_core.documents.Document` objects, strings, or dictionaries with
`page_content`/`content`/`text`.

```python
from langchain_core.documents import Document

def govern_documents(documents, params=None, context=None):
    return [
        Document(
            page_content=doc.page_content.strip(),
            metadata={**dict(doc.metadata or {}), "business_type": "knowledge_record"},
        )
        for doc in documents
        if doc.page_content.strip()
    ]

def chunk_documents(documents, params=None, context=None):
    return documents
```

## KG Stage

The optional `kg` stage builds deterministic event/entity records from the
already chunked documents. It is still a generic platform contract: the platform
does not understand business fields such as `owner_domain` or `record_title`;
the plugin owns that mapping.

When a document is chunked by a registered `plugin:<id>@<version>:chunk` stage
and the same package declares `plugin:<id>@<version>:kg`, KG extraction will use
that plugin stage before falling back to the generic LLM/heuristic extractor.

KG stage functions should return event dictionaries. The runtime converts them
to the existing `IndexRecord(kind=EVENT)` model and persists them through the
normal KG indexer.

```python
def build_kg_events(documents, params=None, context=None):
    events = []
    for index, doc in enumerate(documents):
        meta = dict(doc.metadata or {})
        record_title = str(meta.get("record_title") or "").strip()
        if not record_title:
            continue
        events.append(
            {
                "source_index": index,
                "title": f"领域知识：{record_title}",
                "summary": doc.page_content[:240],
                "content": doc.page_content,
                "references": {
                    "record_id": meta.get("record_id"),
                    "segment_type": meta.get("segment_type"),
                },
                "extra_data": {"kg_builder": "my_business_plugin_v1"},
                "entities": [
                    {"name": record_title, "type": "KnowledgeRecord", "role": "subject"},
                    {"name": meta.get("owner_domain"), "type": "OwnerDomain", "role": "owner"},
                ],
            }
        )
    return events
```

Supported event fields:

- `title`, `summary`, `content`: required logically; missing values are filled from the other text fields.
- `source_index`: optional index of the source chunk document; defaults to output order.
- `document_id`, `chunk_id`: optional. During ingestion the runtime also reads them from chunk metadata.
- `references`, `extra_data`, `metadata`: optional dictionaries stored on the event record.
- `vector`: optional list of floats. Most business plugins should omit this and let the platform store lexical KG only unless they explicitly own vector generation.
- `entities`: optional list of dictionaries with `name`, `type`, `normalized_name`, `description`, `role`, and evidence fields.

KG event `metadata` must not contain reserved platform metadata view keys such
as `_indexed_metadata`, `_display_metadata`, `_evaluable_metadata`,
`_record_identity`, `_retrieval_text`, or `_retrieval_display_content`.
Declare business fields in `metadata_schema.json`; the platform rebuilds its
internal views from that contract.

## Metadata Schema

`metadata_schema.json` declares the business fields a plugin emits. The platform
does not need to understand the business meaning of those fields; it validates
types, required fields, and stage applicability.

```json
{
  "schema": "mimirq.metadata_schema.v1",
  "record_identity": ["record_id"],
  "fields": [
    {
      "name": "record_id",
      "type": "string",
      "required": true,
      "stages": ["governance", "chunk"],
      "filterable": true,
      "display": true,
      "evaluable": true,
      "max_length": 120
    },
    {
      "name": "business_type",
      "type": "string",
      "required": true,
      "stages": ["governance", "chunk"],
      "filterable": true,
      "display": true,
      "evaluable": true,
      "max_length": 120
    },
    {
      "name": "record_type",
      "type": "string",
      "required": true,
      "stages": ["governance", "chunk"],
      "filterable": true,
      "display": true,
      "evaluable": true,
      "max_length": 120
    },
    {
      "name": "segment_type",
      "type": "string",
      "required": true,
      "stages": ["chunk"],
      "filterable": true,
      "display": true,
      "evaluable": true
    }
  ]
}
```

Supported field types are `string`, `integer`, `number`, `boolean`, `array`, and
`object`.

`metadata_schema.fields[]` entries must be objects, and
`metadata_schema.fields[].name` must be a JSON string. Do not rely on scalar
shortcuts such as `true` or `123`; invalid field declarations are rejected before
the platform builds generic index/display/evaluation views.
`metadata_schema.fields[].name` must not start with `_`, and no dotted path
segment may start with `_`. The `_` namespace is reserved for MimirQ platform
views such as `_indexed_metadata`, `_display_metadata`, `_evaluable_metadata`,
and `_record_identity`; KG metadata subpaths such as `metadata._record_identity` are also rejected.
Platform-owned metadata field names are reserved; platform-owned metadata field names such as `source`, `document_id`, `chunk_id`, `dataset_id`, `parser_backend`, and `resolved_chunk_strategy` cannot be declared by plugins.
Use plugin-owned names such as `origin_file`, `record_key`, or
`business_document_key` when the business plugin needs provenance fields.
For KG contracts, `metadata.source` and `metadata.document_id` are rejected for
the same reason; put business references under plugin-owned `metadata.*` fields
or use `references.*` fields for graph references.
`metadata_schema.fields[]` entries are closed contracts; only `name`, `type`,
`required`, `stages`, `filterable`, `display`, `evaluable`, `max_length`, and
`enum` are supported. Put business behavior in plugin code instead of adding
ignored field-level keys.

`required`, `filterable`, `display`, and `evaluable` must be JSON booleans
(`true` or `false`), not strings such as `"false"`; scalar shortcuts are
rejected so platform indexing, display, and evaluation views match plugin intent.
`max_length` must be a JSON integer, not a string. `enum` must be an array; a
scalar enum is rejected so declared value constraints cannot be disabled by
accident.

Contract stage names are `governance`, `chunk`, and `kg`. Use them in
`metadata_schema.fields[].stages` to target platform lifecycle stages. Do not
create business stage names there; model business categories as plugin metadata
fields instead. `retrieval_text_schema.stages` only supports `governance` and `chunk` because it composes document text for indexing. KG event contract fields should use `metadata.*`, `references.*`, or `extra_data.*` paths, for example `extra_data.event_type` or `references.source_id`. KG metadata fields must start with `metadata.`, `references.`, or `extra_data.`.

The platform interprets only schema flags, never business-specific field names:

- `filterable: true` is copied into `_indexed_metadata` for generic metadata filtering/indexing.
- `display: true` is copied into `_display_metadata` for UI and citation summaries.
- `evaluable: true` is copied into `_evaluable_metadata` for regression/golden evaluation.
- `record_identity` is copied into `_record_identity` for source-record aggregation and de-duplication.

Plugins must not write those platform internal view fields directly in document
or KG event metadata. Document plugin outputs are rebuilt from schema views, and
KG event metadata containing reserved platform view keys is rejected.

`record_identity` must be an array of metadata field names declared in
`metadata_schema.fields`. `record_identity` entries must be JSON strings;
scalar shortcuts are rejected so record-level deduplication and retrieval
grouping cannot be disabled by accident.

Retrieval behavior is also schema-driven:

- A metadata filter on a schema-declared metadata field falls back to `_indexed_metadata.<field>` when the top-level field is absent, so callers do not need to hard-code internal view paths.
- Milvus vector search stores `_indexed_metadata` in fixed generic key/value slots and pushes down exact / `$eq` / `$in` filters when the collection schema supports those slots.
- If a legacy Milvus collection does not have the slot fields, search falls back to the old scalar expr and the full metadata filter is still enforced after DB enrichment.
- Candidate de-duplication can cap chunks per `_record_identity` key using `RETRIEVAL_MAX_CHUNKS_PER_RECORD_IDENTITY`.
- Reranker candidates receive a short header from `_display_metadata` and `_evaluable_metadata`, while stored chunk content remains unchanged.
- Retrieval config fingerprints include a non-reversible metadata filter hash and a key/operator summary, not raw filter values.
- Ingestion post-processing preserves `_record_identity` boundaries: small-chunk merging will not merge different records, and global chunk-count truncation is skipped for record-identified chunks.
- Ingestion exact dedup uses content hash plus `_record_identity.key`; near-dedup skips record-identified chunks, so similar templates from different business records are not silently dropped.

During ingestion, plugin chunks keep their business `chunk_strategy` value (for
example `python_plugin` or a plugin-specific strategy name). The platform's
resolved fallback strategy is stored separately as `resolved_chunk_strategy`.
Do not overwrite plugin `chunk_strategy` in post-processing; downstream health,
retrieval, and Golden diagnostics use it to distinguish plugin chunking from
generic platform chunking.
If post-processing merges small chunks inside the same `_record_identity`, it
must invalidate content-derived fields (`content_hash`, `simhash64`,
`chunk_quality`, semantic role/type, and structure) and rebuild merged
`_retrieval_text`. Otherwise the vector/BM25 index can keep only the first
fragment's recall text while the stored chunk body contains multiple fragments.

Business fields such as `region`, `contract_party`, `owner_team`, or
`product_line` belong in plugin schemas. Platform code must not hard-code them.

## Retrieval Text Schema

`retrieval_text_schema.json` defines the recall-optimized text used by vector and
BM25 indexes. It does not replace the stored/display chunk content. The original
content is kept in `_retrieval_display_content`, while the generated index text
is stored in `_retrieval_text`.

```json
{
  "schema": "mimirq.retrieval_text_schema.v1",
  "stages": {
    "chunk": {
      "fields": [
        { "metadata": "business_type", "label": "业务类型" },
        { "metadata": "segment_type", "label": "切片类型" },
        { "content": true, "label": "内容" }
      ]
    }
  }
}
```

`retrieval_text_schema.stages.<stage>` must be an object.
`retrieval_text_schema.stages.<stage>` entries are closed contracts; only
`fields` is supported.
`retrieval_text_schema.stages.<stage>.fields[]` entries must be objects.
`retrieval_text_schema.stages.<stage>.fields[]` entries are closed contracts;
only `metadata`, `content`, and `label` are supported.
`retrieval_text_schema.stages.<stage>.fields[]` entries must set `metadata` or `content: true`.
Use `{"metadata": "<field>"}` to include declared plugin metadata or
`{"content": true}` to include source content; string shortcuts and label-only
no-op entries are rejected.
`retrieval_text_schema.stages.<stage>.fields[].metadata` must be a JSON string;
boolean or numeric shortcuts are rejected before recall text is built.
`retrieval_text_schema.stages.<stage>.fields[].content` must be a JSON boolean;
string or numeric shortcuts are rejected before recall text is built.

Use this for aliases, titles, section names, and business labels that improve
recall. Do not drop source content; the source content remains the display and
evidence body.

## Retrieval Policy

`retrieval_policy.json` declares how plugin metadata can be consumed by generic
retrieval planning and ranking. It is not a business code hook, does not contain
dataset ids, and must not encode Dify/workflow-specific routing. The platform
validates field references against `metadata_schema.json` so adapters and
retrievers can later consume the same contract without hard-coding business
field names.

```json
{
  "schema": "mimirq.retrieval_policy.v1",
  "query_expansion_fields": ["record_title", "aliases", "keywords"],
  "query_expansion_values": [
    { "metadata": "segment_type", "value": "steps", "terms": ["setup steps", "operation guide"] },
    { "metadata": "record_type", "values": ["faq", "help"], "terms": ["help center"] }
  ],
  "filter_fields": ["business_type", "record_type", "segment_type"],
  "boost_fields": [
    { "metadata": "record_title", "weight": 1.8, "match": "contains" },
    { "metadata": "aliases", "weight": 1.5, "match": "overlap" }
  ],
  "anchor_fields": [
    {
      "metadata": "region",
      "weight": 2.0,
      "aliases": {
        "north": ["north", "north district"],
        "south": ["south", "south district"]
      }
    }
  ],
  "rerank_features": ["business_type", "record_type", "segment_type"],
  "fallback": {
    "enabled": true,
    "expand_top_k_multiplier": 2
  }
}
```

Use `query_expansion_values` when a metadata value represents a business-specific
intent that should add recall/ranking terms. The platform treats it as data:
if a record has `segment_type=steps`, the terms are available to generic
retrieval policy scoring without adding adapter code for that business.

`query_expansion_fields`, `filter_fields`, `anchor_fields`, and
`rerank_features` must reference metadata field names declared by
`metadata_schema.json` and available at the `chunk` stage. `filter_fields` must
reference fields marked `filterable: true`; this keeps policy filters aligned
with `_indexed_metadata` and vector-store pushdown support.
Adapters may also use values from `query_expansion_fields` as bounded ranking
hints when the user query already contains those metadata terms. This keeps
business synonyms and titles inside plugin metadata while letting the platform
rank candidates without hard-coded business field names.
When a Dify knowledge map entry declares `plugin_refs`, the adapter also uses
the referenced plugins' `filter_fields` as an allowlist for Dify
`metadata_condition` pushdown. Without `plugin_refs`, legacy metadata filters
keep their existing behavior for compatibility.
Adapters may use `rerank_features` as weaker bounded ranking features when the
query contains values from those declared metadata fields. Use explicit
`boost_fields` when a business field should carry stronger or weighted ranking
intent.

`anchor_fields[]` entries let a plugin declare query-scoping anchors such as
region, product line, department, or jurisdiction. When the query clearly
matches one declared anchor value but a candidate record carries a different
value for the same metadata field, adapters may apply a bounded demotion. The
platform only understands the generic `metadata`, `weight`, and `aliases`
contract; the plugin owns the actual business values and aliases.

`boost_fields[]` entries are objects with `metadata`, optional `weight`, and
optional `match`. Supported match modes are `exact`, `contains`, and `overlap`.
Weights must be positive and bounded. These are planner/reranker hints, not a
guarantee that every retrieval profile will apply them.

`fallback.enabled` and `fallback.expand_top_k_multiplier` describe whether the
generic planner may widen recall when first-pass evidence is weak. This remains
platform-owned execution policy; the plugin only declares that widening is
acceptable for this business package.
Dify adapter entries with `plugin_refs` apply the largest enabled fallback
multiplier from the referenced plugins to the internal candidate window, still
bounded by `DIFY_EXTERNAL_KNOWLEDGE_INTERNAL_TOP_K_MAX`; the external `top_k`
returned to Dify is unchanged.

## Golden Rules

`golden_rules.json` is the plugin-level evaluation declaration. The first version
is declarative: it records which metadata fields define an expected hit and which
query templates the plugin can use later for generated test cases.

```json
{
  "schema": "mimirq.golden_rules.v1",
  "expected_metadata": ["record_id", "segment_type"],
  "template_selector_fields": ["segment_type", "record_type"],
  "tag_fields": ["record_type", "segment_type"],
  "query_templates": {
    "knowledge_record": [
      "{record_title}的处理流程是什么？",
      "{record_title}需要关注哪些条件？"
    ],
    "faq": ["{question}"]
  }
}
```

`template_selector_fields` tells the platform which plugin metadata fields select
the `query_templates` bucket. `tag_fields` controls which metadata values become
generated Golden case tags. If `template_selector_fields` is omitted, MimirQ
only tries the `default` query template bucket. If `tag_fields` is omitted, the
draft only carries platform tags such as `plugin:<id>` and `golden_draft`.
Business-specific selector and tag fields must be declared in the plugin rule
file; they are not platform defaults.
`expected_metadata`, `template_selector_fields`, and `tag_fields` must be arrays
of plugin metadata field names declared by `metadata_schema.json`; strings and
other scalar shortcuts are rejected instead of being silently ignored.
`expected_metadata` is required for executable Golden plugins and must declare
at least one field, so generated cases have a concrete metadata hit criterion.
`expected_metadata`, `template_selector_fields`, and `tag_fields` entries must be JSON strings.
The platform does not coerce booleans or numbers into business field names.
Fields listed in `expected_metadata` must also set `evaluable: true`, because
Golden draft generation and regression scoring read plugin-owned expectations
from `_evaluable_metadata` instead of guessing raw business metadata fields.
`query_templates` must be an object. `query_templates.<bucket>` must be an array of JSON strings.
Invalid template structures are rejected before Golden drafts are generated.

Golden drafts are emitted as `mimirq.regression_cases.v1` bundles. For a
review-only bundle, call:

```text
POST /api/v1/pipeline/plugins/golden-draft
```

After human review, either import the bundle through the existing regression
case import API:

```text
POST /api/v1/evaluations/ragas/regression/cases/import
```

Or use the pipeline-side atomic helper, which builds the draft and imports it in
one request with the same regression import rules:

```text
POST /api/v1/pipeline/plugins/golden-draft/import
```

Plugin-generated `extra.expected_metadata` is preserved on regression cases, so
evaluation can later assert business-level expectations without hard-coding
business fields into the platform.
Generated cases also keep plugin provenance in `extra.plugin_id`,
`extra.plugin_version`, `extra.plugin_ref`, and `extra.plugin_package_hash`.
Use those fields to trace which tested plugin package produced a Golden case and
to explain evaluation diffs after a plugin contract or implementation changes.
By default, Golden draft/import only reads chunks produced by the selected
plugin ref. `include_unmarked_chunks=true` is a backend debug escape hatch and
is rejected unless `PYTHON_PIPELINE_PLUGIN_ALLOW_UNMARKED_GOLDEN_CHUNKS=true`;
keep it disabled for production gates so Golden cases stay tied to
plugin-owned chunk outputs. Normal flows use only chunks produced by the selected plugin.
Regression runs and retrieval-only gates expose `expected_metadata_hit_rate` and
`expected_metadata_recall` from those fields.
`scripts/regression_gate.py --generate-thresholds-out ...` includes those two
metrics in its default generated top-level and slice thresholds, so a plugin
Golden baseline can become a CI gate without hand-copying metric keys.
When the baseline run uses `--plugin-golden-ref`, the generated thresholds also
include a compact `thresholds case_source` section with the plugin ref, id,
version, package hash, and draft item count. Runtime import details such as
`case_ids` are deliberately excluded from that baseline file.

The chunk preview workbench plugin panel exposes a one-click "generate and
import Golden" action for the selected dataset. It calls the pipeline-side
atomic helper with `overwrite=false` by default. It also exposes "import and
run Golden", which imports the cases and immediately starts a retrieval-only
regression run through:

```text
POST /api/v1/evaluations/ragas/regression/runs
```

The frontend deep-links the result to:

```text
/evaluations?tab=regression&dataset_id=<dataset_id>&run_id=<run_id>
```

That link is the operator handoff from plugin chunking into retrieval quality
review: the regression page opens the selected dataset and polls the specific
`run_id` until the run finishes.
Domain presets in the workbench must resolve executable registered plugin refs
from `GET /api/v1/pipeline/plugins`; they should not hard-code Python import
paths, otherwise the manifest, local test report, and Golden draft checks are
bypassed.

For a command-line live smoke on an already-ingested dataset, run:

```bash
python scripts/plugin_golden_closed_loop_smoke.py \
  --base-url http://127.0.0.1:8000 \
  --dataset-id 00000000-0000-0000-0000-000000000000
```

If `--plugin-ref` is omitted, the script selects an executable plugin that has
a `chunk` ref and `golden.enabled=true`. It imports plugin Golden cases, starts
a retrieval-only run with `metrics=[]`, polls the run detail, and fails unless
`expected_metadata_hit_rate` and `expected_metadata_recall` are present and meet
the configured thresholds. Use this smoke after ingestion/indexing to verify the
whole business plugin loop, not just local plugin syntax.
The JSON output includes `plugin_source.plugin_id`,
`plugin_source.plugin_version`, `plugin_source.plugin_ref`, and
`plugin_source.plugin_package_hash`, matching the CI gate provenance fields.

For a command-line live smoke that starts from a local source directory, uploads
the corpus with the plugin pipeline, waits for document processing/indexing, and
then runs the same Golden regression, use:

```bash
python scripts/plugin_corpus_closed_loop_smoke.py \
  --base-url http://127.0.0.1:8000 \
  --source-dir /path/to/domain-corpus \
  --plugin-ref plugin:<plugin-id>@<version>:chunk \
  --include-source-root-name \
  --overwrite-goldens
```

If `--dataset-id` is omitted, the script creates an isolated dataset. It sends
the selected chunk ref through the upload `pipeline` JSON as
`chunk_python_plugin`. If the selected plugin manifest exposes `refs.governance`, the smoke also passes `governance_python_plugin`; it does not derive governance refs from chunk refs. If the selected plugin manifest exposes `refs.kg`, the smoke also passes `kg_python_plugin` and enables KG/event/entity indexing so the full plugin-owned extraction path is exercised.
By default it reads `suggested_pipeline_patch` from
`/api/v1/pipeline/plugins` for the selected plugin ref, so plugin-specific
parameters stay in the plugin manifest. The script's activation refs still come from plugin `refs`; `suggested_pipeline_patch` must not carry
`governance_python_plugin`, `chunk_python_plugin`, `kg_python_plugin`, platform
chunk strategy parameters, or built-in governance rule knobs. Pass
`--pipeline-patch-json` only when you intentionally want to override that
manifest patch for a live run; `--pipeline-patch-json` cannot carry activation refs either,
and the script does not know business parameter names.
It skips zero-byte files by default, checks that every non-empty completed
document has chunks, and then delegates to
`scripts/plugin_golden_closed_loop_smoke.py` for the retrieval-only Golden run.
If the directory name itself carries business meaning, pass
`--include-source-root-name`; otherwise relative source paths are computed from
inside the selected source directory with no business-specific heuristics.
Use this smoke when the requirement is to prove ingest + indexing + Golden end
to end, not just that an existing dataset can import plugin cases.

For CI, nightly, or release gating, `scripts/regression_gate.py` can use plugin
Golden as the case source directly:

```bash
python scripts/regression_gate.py \
  --base-url http://127.0.0.1:8000/api/v1 \
  --user-id ci \
  --dataset-id 00000000-0000-0000-0000-000000000000 \
  --plugin-golden-ref plugin:domain-knowledge-demo@1.0.0:chunk \
  --metrics "" \
  --thresholds ci/domain-knowledge-demo.thresholds.json \
  --out-report-json artifacts/domain-knowledge-demo.regression-gate.json
```

`--plugin-golden-ref` must be a registered `plugin:<id>@<version>:chunk` ref.
Golden import does not accept governance/KG refs or ad-hoc Python import paths.

This route calls `POST /api/v1/pipeline/plugins/golden-draft/import`, consumes
the returned `case_ids` directly, then starts
`POST /api/v1/evaluations/ragas/regression/runs`. Use retrieval-only thresholds
such as `expected_metadata_hit_rate` and `expected_metadata_recall` to catch
business metadata regressions before a plugin package is promoted.
The gate report JSON includes `case_source.kind=plugin_golden`,
`case_source.plugin_ref`, `case_source.plugin_package_hash`, and
`case_source.import_result`, so a failing CI artifact can be traced back to the
exact tested plugin package instead of only to the final regression run.
If a thresholds file declares `case_source.plugin_ref` or
`case_source.plugin_package_hash`, the gate verifies those fields against the
current plugin Golden import before starting the regression run. A `plugin package hash`
mismatch means the baseline was produced by different plugin code
or resources, so regenerate the thresholds from the current executable plugin
instead of comparing incompatible baselines.

## Local Test

Create a sample input JSON:

```json
[
  {
    "page_content": "sample text",
    "metadata": { "source": "sample.txt" }
  }
]
```

Run the local test before using the plugin in the system:

```bash
python scripts/pipeline_plugin_runner.py test plugins/pipelines/domain-knowledge-demo \
  --input samples/domain-knowledge-demo.json \
  --stage governance \
  --stage chunk
```

When multiple stages are requested, the runner executes them in pipeline order
using the previous stage output as the next stage input. For example,
`governance` output is fed into `chunk`, so required metadata added during
governance is validated again on the final chunks. If the plugin declares a KG
entry, append `--stage kg` to validate that deterministic KG event extraction
also runs from the plugin package.

The command writes `.mimirq-plugin-test.json`. If the plugin declares
`golden_rules.json` and has a `chunk` stage, the report must also contain
`golden_draft.passed=true`; otherwise the registry marks the plugin as
`golden_missing` and it is not executable. After the report passes, refresh the
frontend plugin selector. The plugin appears as:

```text
plugin:domain-knowledge-demo@1.0.0:governance
plugin:domain-knowledge-demo@1.0.0:chunk
```

Before handing a plugin to another environment, run the generic release gate:

```bash
PLUGIN_RELEASE_GATE_PLUGIN_DIR=plugins/pipelines/domain-knowledge-demo \
PLUGIN_RELEASE_GATE_SAMPLE=samples/domain-knowledge-demo.json \
make plugin-release-gate
```

The gate combines the local stage test, current package-hash verification,
generic chunk readiness, and declared Golden draft availability into
`mimirq.plugin_release_gate.v1`. It intentionally keeps only aggregate evidence
such as counts, refs, readiness checks, and package hash. It does not include
chunk examples or content previews; generate a chunk report separately when you
need local debugging context.

To review or import the exact generated Golden cases before touching a dataset,
export a local regression bundle from the same sample:

```bash
python scripts/pipeline_plugin_runner.py golden-draft plugins/pipelines/domain-knowledge-demo \
  --input samples/domain-knowledge-demo.json \
  --stage governance \
  --stage chunk \
  --stage kg \
  --dataset-id 00000000-0000-0000-0000-000000000000 \
  --out artifacts/domain-knowledge-demo.golden.json
```

The output is a `mimirq.regression_cases.v1` bundle with
`review_only=true` and `reference_source_mode=local_sample_synthetic`. Its
`document_id` and `chunk_id` values are deterministic local placeholders, so do
not import it into a real dataset. Use it for plugin review, snapshot tests, or
CI fixtures. To create importable Golden cases for production, ingest the data
first and call `POST /api/v1/pipeline/plugins/golden-draft/import`, which uses
real indexed chunk ids. Local bundles still include the same plugin provenance
fields in `extra`, but they are not production evidence because their reference
sources are synthetic.

`scripts/regression_gate.py` refuses to import `review_only=true` bundles or
items by default. Use `--skip-import` only when the referenced questions already
exist as real regression cases in the target dataset.
The regression case import service also rejects items marked with
`extra.review_only=true` or `extra.reference_source_mode=local_sample_synthetic`.

## Runtime

The backend scans plugin directories at runtime. Adding a new tested plugin
package does not require restarting the backend. The plugin selector calls:

```text
GET /api/v1/pipeline/plugins
```

The ingestion pipeline only executes plugin refs returned as executable by this
endpoint.
The response includes `package_hash` and a compact `test_report` summary
(`tested_at`, stage counts, and Golden draft count), so operators can verify
which locally tested package is currently selectable before applying it to a
dataset.
If one plugin package has an invalid manifest or contract file, the list endpoint
still returns the valid plugins and reports the broken package under `errors`.
Execution and Golden endpoints remain strict: a broken, stale, unpublished, or
untested plugin ref is rejected instead of being silently skipped.
When a plugin entry imports local helper modules, the runtime clears plugin-local
module and bytecode caches before loading the entry. This keeps helper changes
hot-reloadable, but the plugin still becomes executable only after the local
test report is refreshed and its `package_hash` matches. Plugin-local modules
are removed from `sys.modules` after loading, and any previously loaded external
module with the same name is restored, so helpers such as `rules.py` or
`json.py` do not pollute the backend process. The import/cache mutation path is
guarded by a process-local lock so concurrent requests cannot cross-import
another plugin's helper modules; the returned plugin functions run outside that
lock. Function bodies may also lazily import local helper modules, including
generator-style plugin functions that import helpers while yielding documents;
the runtime temporarily restores the plugin directory for the function call or
iterator step and then removes plugin-local modules again before control returns
to the caller. A paused generator must not leave the plugin directory on
`sys.path`.
