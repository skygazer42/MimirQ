# MimirQ “40 项优化（性能/成本 + 可靠性）”设计稿

**Date:** 2026-02-15  
**Target:** 默认 Docker Compose 一键启动（`make up` / `make up-web`）  
**Scale assumption:** 5k–50k 文档、1–10 并发查询、偶尔批量入库  

---

## 1) 背景与动机

MimirQ 是一个以 RAG 为核心的知识库问答系统。当前仓库已经具备较完整的功能（解析/切块/混合检索/流式对话/权限裁剪/评测等），但在默认 Docker Compose 一键启动模式下，仍存在以下常见痛点：

- **成本（Cost）**
  - API 成本：Embedding 与 Chat 的 token/调用量缺少系统性约束与归因，容易“越用越贵”。
  - 机器成本：默认 Compose 常驻资源偏高（Milvus/etcd/minio/worker 等），对小团队机器不友好。
- **性能（Performance）**
  - 入库吞吐不稳定：批量入库容易遇到失败重试、重复计算、长尾延迟与峰值内存抖动。
  - 查询长尾：检索 overfetch、融合/重排、权限裁剪与上下文拼装可能导致 p95 延迟偏高。
  - 前端卡顿：大列表、chunk 预览、报告/图表页存在首屏与交互性能风险。
- **可靠性（Reliability）**
  - Compose 冷启动依赖抖动导致 worker crash loop。
  - 缺少统一的基线度量与一键诊断，导致“感觉变慢/变贵”但难以定位。

本设计稿将优化工作组织成一套可验证的 40 项优化计划：先建立**最小度量基线**，再做默认 Compose 的“稳/省/快”快赢，随后深入入库与检索链路，最后收尾前端性能。

---

## 2) 目标（Goals）

### 2.1 产品体验目标（面向默认 Docker Compose）

- `make up` / `make up-web` 的默认体验更稳定、更省资源、更易诊断。
- 中等规模（5k–50k 文档）下：
  - **入库**：吞吐更平滑；失败能恢复；尽量避免重复 embedding 与重复写向量。
  - **查询**：TTFT（首 token）与总耗时的 p95 更低；检索 overfetch 更少。
  - **前端**：关键页面在大数据集下不卡顿（列表/预览/报告页）。

### 2.2 成本目标（API + 机器）

- **API 成本**：对 chat 与 embedding 的 token 使用进行归因、观测与可控（缓存/路由/去噪）。
- **机器资源**：默认常驻资源可控；提供可选的 `lite` 方案显著降低内存占用。

---

## 3) 非目标（Non-Goals）

- 不做“推倒重来式”架构替换（例如整体替换向量库/全量重写 RAG pipeline）。
- 不以“生产级多副本高可用”为主要目标（本轮以单机 Compose 默认体验为主）。
- 不追求绝对数值承诺（不同机器/数据差异大），以**基线对比 + 可观测指标 + 可回滚开关**作为验收基础。

---

## 4) 验收指标（Metrics & Acceptance）

### 4.1 入库链路（A）

- 吞吐：文档/分钟、页/分钟（固定样本 corpus 复现对比）。
- 稳定：失败率、重试次数分布、可恢复性（checkpoint 生效）。
- 分解耗时：下载（URL）/解析/切块/embedding/向量写入/DB 写入。

### 4.2 查询链路（B + 成本）

- 延迟：TTFT（首 token）与总耗时的 p50/p95。
- 检索分解：vector/BM25/融合/重排/ACL 裁剪耗时与候选数。
- Token：prompt/completion tokens（优先使用 provider usage；否则 best-effort 估算并标注来源）。
- 缓存：命中率、节省 token/延迟的估算。

### 4.3 前端（C）

- 大列表：滚动/筛选的主线程占用与掉帧体感；首屏加载时间。
- chunk 预览：滚动与切换 pipeline 的交互响应。
- 报告/图表：避免一次性渲染超大数据导致卡死。

### 4.4 资源（E）

- Compose 常驻资源：空载/低载时各容器 RSS、CPU idle、磁盘增长。
- 高载峰值：批量入库 + 并发查询时峰值 RSS/CPU。
- 日志体积：长期运行不会被日志吃满磁盘（log rotation 生效）。

---

## 5) 最小基线方案（Baseline Harness）

新增一个“最小但可重复”的性能基线工具，满足：

- 可在本地一键运行，不依赖外部可观测系统。
- 支持 `LLM_MOCK_ENABLED=1`：端到端不调用外部 LLM，不烧钱，适合作为回归基线。
- 输出结构化结果到 `runs/perf/...`，便于对比与在 CI 中作为 informational gate。

## 6) 40 项优化清单（Backlog）

> 注：每项都要求具备“验证方式”。其中带 **Optional** 的表示默认不启用（以避免改变现有默认行为或引入风险），但会提供清晰的配置与回滚路径。

### 6.1 基线与度量（6）

1. Perf 基线脚本：入库 + 查询（默认）
2. LLM Mock 的端到端基准模式（默认）
3. Request ID 贯通（默认）
4. Token/费用可观测（默认记录；展示可选）
5. 检索分解耗时指标（默认）
6. `make perf-smoke`（默认）

### 6.2 Docker 默认成本/可靠性（8）

7. `docker-compose.lite.yml`（Optional）
8. Compose 资源旋钮标准化（默认）
9. Redis 内存上限 + 淘汰策略（默认）
10. Postgres 中规模默认调优（默认）
11. Docker 日志滚动（默认）
12. Worker 启动鲁棒性（默认）
13. 数据目录/卷职责明确化（默认）
14. 一键 Compose 诊断脚本（默认）

### 6.3 入库/解析/切块（12）

15. 入库幂等锁（默认）
16. 进度上报更真实（默认）
17. 阶段性 checkpoint（Optional，逐步启用）
18. 解析器调用统一重试/超时/错误分级（默认）
19. 上传去重（SHA256 + pipeline_hash）（Optional）
20. Embedding 批量 + 并发限流（默认）
21. Embedding cache 命中率指标（默认）
22. 向量写入批次自适应（默认）
23. 解析内存峰值控制（默认）
24. 失败信息更可行动（默认）
25. Worker 并发默认更保守（默认）
26. Precheck 前置化（Optional）

### 6.4 检索/回答延迟 + token 成本（8）

27. 强制 scope 检索（默认）
28. top_k/fetch_k/RRF 参数中规模默认值调优（默认）
29. BM25 缓存增量失效策略（默认）
30. 检索候选短 TTL 缓存（Optional）
31. 安全的回答缓存（Optional）
32. 动态模型路由（Optional）
33. 上下文压缩与去噪（默认）
34. 慢/贵反馈到 UI（默认）

### 6.5 前端性能（6）

35. 大依赖按路由拆包（默认）
36. 大列表虚拟化（默认）
37. Chunk 预览渲染优化（默认）
38. React Query 缓存与并发控制（默认）
39. 大 JSON / 图表渲染降载（默认）
40. 诊断页增强（默认）

---

## 7) 交付节奏（Phases）

- Phase 0：最小度量 + 基线（1–6）
- Phase 1：Compose 默认稳/省（7–14）
- Phase 2：入库链路吞吐 + 可恢复（15–26）
- Phase 3：检索延迟 + token 成本（27–34）
- Phase 4：前端性能（35–40）

---

## 8) 风险控制与回滚

- 所有高风险优化（缓存、动态路由、lite compose）必须 **Optional** 且具备回滚开关。
- 缓存类优化必须 fail-closed，key 必须包含足够的权限上下文（tenant/dataset/pipeline/account 等）以避免越权或串数据。
- 自动重试必须有上限、退避与可观测日志，避免重试风暴。

---

## 9) 测试/门禁策略

- 本地门禁：`make verify`、`make enterprise-checks`。
- 新增：`make perf-smoke`（默认作为轻量验证/信息输出，必要时再升级为 gate）。
- TDD：对幂等/缓存 key/错误分级/参数边界等高风险点补单测；对端到端链路补 LLM mock 集成测。
