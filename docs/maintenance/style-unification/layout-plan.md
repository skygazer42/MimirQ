# App 目录与模块命名规范化实施计划

> 执行方式：在 `feat/ragvia-ui` 原工作区持续执行，独立目录并行审查，共享入口与调用方由主代理统一更新。

**Goal:** 逐项核对整个 `app` 的目录、模块和依赖归属，合并重复维护点，使用能够表达实际职责的名称。

**Architecture:** 沿用已确认的分层：API、业务服务、ORM、内部契约、解析、RAG、存储与共同基础设施。目录调整与定义、调用方、动态装配和开发文档一起更新；不保留旧路径转发。

**Tech Stack:** Python 3.11、FastAPI、Pydantic v2、SQLAlchemy、Ruff。

**Spec:** [现有模块边界](../../development/module_boundaries.md)及本轮用户要求；继续执行已确认的 Python 开发规约。

## 全局约束

- 保留当前分支和既有未提交工作；本轮不自动提交、推送或创建工作区。
- 610 个 Python 测试保持本轮开始时的字节，不新增、不修改、不运行 pytest。
- 外部路由、Pydantic 契约、数据库表结构、索引、关系、资源路径、任务入口和模型选择行为保持。
- `models` 持有数据库实体，`api/schemas` 持有 HTTP 数据模型，`types` 持有内部共享契约；不按共同的“类”形式合并。
- 只有相同维护职责才合并；独立资源、算法、依赖和框架注册边界保留。第三方派生实现按来源保留。

## 验证重点

- 模块迁移后的普通、局部、相对和动态导入必须指向现存定义。
- 通用基础设施不为日志、HTTP 环境或哈希导入 RAG。
- 日志迁移保留 logger 名称、请求上下文、JSON 配置及解析子进程的初始化格式。
- ORM 注册没有漏表、重复映射或关系求值变化；API 冷导入及完整 OpenAPI 没有新增差异。
- 文件清单区分内容审查、命名/依赖审查及仅机械更新，不用静态通过冒充业务验收。
