# Agent Note: 配置校验直接依赖声明类型与实际所有者

Status: implemented

## Problem

配置校验模块先把依赖设为 None，再由配置模块在导入后注入 14 项函数和常量。读取一个已经声明的数字字段还要经过字段名字符串、getattr、转换函数和校验包装，字段、默认值与限制分散在多层调用中，签名也没有说明 Settings 契约。

## Decision

Settings 继续负责字段声明、Pydantic 校验入口及既有 27 段调用顺序。归一化和启动校验由现有 config_validation 模块负责；它直接导入环境及检索规则的实际所有者，Settings 只在 TYPE_CHECKING 下导入，避免运行时反向依赖。原有配置模块继续直接导出三个已被 JWT、设置 API 和对象存储调用的公共函数。

校验入口接收 Settings，已声明字段直接读取；字段名动态读取只保留在确实复用的选择归一化和条件赋值函数。8 个私有取值包装退出，标量范围检查保留在当前模块。原有 or 默认规则继续生效，尤其是零值是否采用默认值，不在风格重构中改变。外部 JSON、URL、UUID、鉴权配置和生产环境限制继续在真实边界校验，错误及警告内容保留。

热加载直接读取 OpsConfigSnapshot 的必填属性与配置键。retrieval_fingerprint 是包含 schema、hash 和 config 的字典，原来的字符串转换参与组合哈希，必须保留；不能顺手替换成只取 hash 或重新序列化 JSON。快照脱敏与表示转换保持原样。

`app/core/build_info.py` 负责构建 SHA 和时间的环境读取。公开元信息、运维快照与管线 provenance 直接导入这一实际所有者，五份相同函数体合并成两个函数。环境变量名称、优先级、选中值之后才 strip、无值返回 None 的规则保留；导入时不缓存环境，调用时读取。模块只依赖标准库，避免由业务服务反向依赖 API 路由。

## Alternatives considered

- 继续导入后注入可以保持校验模块不导入应用代码，但依赖只在初始化顺序中隐式成立；直接导入现有无反向配置依赖的规则模块更便于追踪。
- 统一成字段名、默认值、限制和消息的规则表可以压缩重复校验，但会把有顺序、有分支及可能修改配置的启动流程变成解释器。本批保留顺序调用和直接属性，不新增配置框架。
- 把所有校验并回 Settings 可以减少模块引用，但会再次混合 1,316 个字段声明和启动规则；复用现有两个模块，不增加新文件或服务层。
- 三处构建信息各自读取能避免相互导入，但它们采用相同规则，修改优先级会产生多处维护；独立的标准库模块给已有复用规则一个所有者，不引入转发包装。

## Consequences

字段、默认值和限制可在同一调用中读取，校验模块的 57 个函数均有参数与返回类型。运行时注入和重复包装减少，但新增字段仍需在所属校验段维护；公开导出保留现有导入路径。未来若这些规则模块新增配置依赖，必须重新核对导入环路，不能恢复隐式注入。

53 个原有校验函数在声明字段、标量类型和包装展开的明确规则下与修改前 AST 一致；4 个迁移函数与 8 项常量原样匹配。Settings 完整类 AST、439 项配置导入、313 处确定调用及两个热加载函数的源码契约已核对。静态比较曾抓到并修正一处自动改写丢失括号的问题；最终比较通过。按用户要求未新增、扩写或运行 Python 测试，未导入业务模块，运行时回归仍未验证。

历史记录核对：当前两篇数据集与权限配额决定分别约束业务所有者和配额政策，与本篇配置依赖关系无关，保留原篇；没有其他活跃配置专篇。
