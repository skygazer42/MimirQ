> 调研中国市场刚需场景：等保 2.0 / 个保法 / 数安法 / 金融监管 / 信通院测评 的合规自动化 RAG 系统。覆盖：条款比对 / 红线检测 / 合规报告生成 / 政策版本管理。**调研型 plan**，不写代码，输出落地路径与决策门槛。
>
> 创建日期：2026-05-07
> 来源：`rag-system-landscape-2026-q2-supplement.md` 第 6.4 + 第 7.2 P1-1
> 论据：中文场景刚需（中文 vertical 护城河延伸），海外 / 开源进不来
>

## 2 中国合规场景拆解

### 2.1 4 类合规客户

| 客户类型 | 痛点 | 单项目预算 |
|---|---|---|
| **大型企业法务** | 内部合规手册 + 合同审查 + 政策更新 | ¥50-200 万 |
| **律所** | 案例 / 法规检索 + 起诉状起草 | ¥10-50 万 |
| **金融机构合规部** | 反洗钱 / 反欺诈 / KYC / 监管报送 | ¥100-500 万 |
| **政府监管 / 信通院** | 合规检查 / 备案审查 / 大模型测评 | ¥50-300 万 |

### 2.2 5 个具体子场景（按需求强度排序）

#### 2.2.1 条款比对（contract clause matching）

- **场景**：客户上传合同 / 政策，系统自动找出与基线（公司模板 / 行业标准）的差异条款
- **MimirQ 适配度**：★★★★（KG + 解析 + 行业规则库可直接用）

#### 2.2.2 红线检测（red-line detection）

- **场景**：客户上传文档，系统找出违反法规 / 内部政策的条款（如"违反个保法第 X 条"）
- **MimirQ 适配度**：★★★★（KG 关联法规条款，industry_rules 适合做规则）

#### 2.2.3 合规报告生成（compliance report generation）

- **场景**：自动生成等保 2.0 测评报告 / SOX 合规报告 / 信通院备案材料
- **MimirQ 适配度**：★★★（需要专属 schema + 报告模板）

#### 2.2.4 法规版本追溯（regulatory version tracking）

- **场景**：法规修订后，自动找出受影响的客户合同 / 政策 / 业务流程
- **MimirQ 适配度**：★★★（KG snapshot 影响分析直接对接）

#### 2.2.5 合规知识问答（compliance Q&A）

- **场景**：员工 / 客户询问"这个操作违反个保法吗"，系统给出答案 + 法规依据
- **MimirQ 适配度**：★★★★★（标准 RAG 场景，已有能力）

## 4 MimirQ 现状对照

### 4.1 现有能力 vs 合规需求

| 合规能力 | MimirQ 现状 | 缺口 |
|---|---|---|
| 法规 / 合同解析 | deepdoc 已支持 | 缺**条款级 parser**（现到段落） |
| 法规 KG | 已有通用 KG extraction | 缺**法规专属 schema**（条 / 款 / 项 / 条文 ID） |
| 行业规则库 | 已有（P0-1 产品化中） | 需扩**红线规则 schema** |
| 检索 + 重排 | hybrid + reranker | 通用够用 |
| Citation | 已规划（rag-evaluation） | 法律场景**法条引用必须精确到 ID + 版本** |
| KG 影响分析 | 已规划（rag-kg-snapshot P1） | 直接复用 |
| 报告生成 | IBM 蓝图结构化输出 | 缺**法律 / 等保 / SOX 模板** |
| 政务合规部署 | — | 缺**等保 2.0 部署文档** + 离线模式 |

### 4.2 缺口汇总

1. **条款级 parser**（核心）—— 法规 / 合同必须切到 *条 / 款 / 项* 级别，不是段落
2. **法规专属 KG schema** —— `Article(id, version, effective_date, jurisdiction) ← Clause ← Item`
3. **红线规则 schema** —— `RedLineRule(law_ref, severity, condition, fix_suggestion)`
4. **法律 / 等保模板** —— 报告生成模板库
5. **政务合规部署模式** —— 等保 2.0 三级 + 政务专网（与第 6 章空白 6 边缘 RAG 协同）
6. **法规版本管理** —— "自 X 日施行 / 修订" 时序 + 影响分析

## 5 接入路径 + 落点设计

### 5.1 6 个落点

| 落点 | 文件路径 | 工作量 |
|---|---|---|
| **A 条款级 parser** | `app/parsing/parsers/legal_article_parser.py` | ~400 行 |

| **F 前端合规面板** | `web/app/governance/compliance/` | ~700 行 |
| **合计** | | **~2200 行 / 3-4 周** |

### 5.2 落点 A：条款级 parser

**目标**：把 `《个人信息保护法》第二十三条` 切成 `第 23 条 / 第 1 款 / 第 (一) 项` 三级嵌套节点

**复用资产**：
- `app/parsing/parsers/` 既有 25+ parser
- `app/rag/chunking/strategies/outline.py` 中文标题解析（"第 1 章 / 一、 / （一）"）
- `app/rag/chunking/utils/heading_parsing.py:parse_cn_prefixed_heading`

**关键算法**：
- 中文法规标准结构：`编 → 章 → 节 → 条 → 款 → 项 → 目`
- 正则 + LLM fallback（针对非标准文档）

### 5.3 落点 B：法规 KG schema

**目标**：扩 KG ontology 加法规专属节点类型

**复用资产**：
- `app/rag/kg/ontology.py`（已有 ontology）
- `app/rag/kg/snapshot.py`（版本快照基础）
- `rag-kg-snapshot-deep-dive-2026-q2.md` P1 影响分析（k-hop BFS）

**新增节点类型**：
```python
@dataclass
class LegalArticle:
    id: str                    # 唯一 ID（如 "PIPL-Art-23"）
    law_ref: str              # 法律名称
    version: str              # 版本（"2021-11-01" / "2024-XX 修订"）
    effective_date: date      # 施行日期
    jurisdiction: str         # 管辖（中国 / 各省）
    clauses: list[Clause]     # 条款
```

### 5.4 落点 C：红线规则库

**目标**：industry_rules 扩展，支持红线规则

**复用资产**：
- `app/rag/industry_rules/`（P0-1 已产品化）
- 现有 `IndustryRuleset` schema 兼容

**扩充 yaml**：
```yaml
# rulesets/finance_compliance/red_lines.yaml
- id: PIPL_Art_23_violation
  law_ref: PIPL-Art-23
  severity: high
  condition: "向境外提供个人信息且未单独同意"
  fix_suggestion: "增加单独同意机制 + 数据出境安全评估"
```

### 5.5 落点 D：合规检查 workflow

**目标**：客户上传文档 → 系统自动检查违规

**复用资产**：
- `app/rag/workflows/base.py:BaseWorkflow`
- `app/rag/workflows/self_rag.py`（critic 模式）
- `app/rag/industry_rules/`（红线规则匹配）

**算法**：
1. 文档 → 条款级 parser（落点 A）
2. 每条款 → KG 查询关联法规
3. 每条款 → 红线规则匹配（rule engine + LLM）
4. 输出违规列表 + 风险等级 + 法条引用

### 5.6 落点 E：合规报告生成

**目标**：等保 2.0 / SOX / 信通院 / 内部合规报告自动生成

**复用资产**：
- `rag-ibm-champion-blueprint-2026-q2.md` Pydantic SO
- 现有 HTML 单文件报告框架

**模板库**：
```
app/rag/compliance/templates/
├── dengbao_2_grade3.yaml      # 等保 2.0 三级
├── sox_404.yaml
├── pipl_dpia.yaml             # 个保法 DPIA
├── tcgi_lmrm.yaml             # 信通院大模型备案
└── internal_compliance.yaml
```

### 5.7 落点 F：前端合规面板

**目标**：客户用的合规工作台

**复用资产**：
- P0-1 行业规则库 UI 风格
- `kg-snapshots` 的 diff 视觉
- `rag-evaluation` 报告 HTML 模板

**4 Tab**：
1. **法规库**：法规 + 版本 + 检索
2. **红线检查**：上传文档 → 违规列表
3. **影响分析**：法规变更 → 受影响合同
4. **合规报告**：模板选 + 生成

## 6 评测集设计

### 6.1 法规理解评测

| 集名 | 来源 | 规模 |
|---|---|---|
| LegalBench-CN（如可申请） | 中文法律组 | 待补 |
| 自建：个保法 50 题 | MimirQ 内建 | 50 题 |
| 自建：等保 2.0 50 题 | MimirQ 内建 | 50 题 |
| 自建：金融合规 50 题 | MimirQ 内建 | 50 题 |

### 6.2 红线检测评测

- 准备 100 份合同（50 合规 + 50 含违规）
- 标注每份违规条款 + 对应法规
- metric：精确率 / 召回率 / F1（违规条款匹配）
- 失败模式：误报（合规当违规）/ 漏报（违规未发现）

### 6.3 影响分析评测

- 模拟 5 次法规修订（如个保法修订）
- 标注每次修订的"应受影响合同 / 政策清单"
- metric：召回率（找到多少应该影响的）/ 精确率（错报多少）

### 6.4 报告质量评测

- 生成 10 份报告（等保 / SOX / DPIA 各 3-4 份）
- 律师人工评审：完整性 / 准确性 / 可读性 1-5 分
- 与人工编写报告对比

## 9 风险 + 范围之外

### 9.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 法律责任风险 | LLM 误报致律师失误 | 明确 disclaimers + 不替代律师审核 |

| 信通院备案要求 | 大模型服务需备案 | P3 提前备案 |
| 竞品先入 | Harvey 中国版 / 北大法宝 AI | 中文 vertical + 开源 + 等保 2.0 |
| 律师抵触 | "AI 抢饭碗" | 定位 *律师助手* 而非 *律师替代* |

### 9.2 范围之外（明确不做）

- 不做合同生成（起草是 Spellbook 主战场，避其锋芒）
- 不做案例预测（类似 Lex Machina，需要深度 vertical 数据）
- 不做诉讼策略推荐（律师专业边界）
- 不做大众法律咨询 To C（监管风险高）
- 不做美国 / 欧洲法律（无法律基础）
- 不做学术法律研究（教科书市场太小）

### 9.3 政策红线（必须遵守）

- 不引导客户违反法律
- LLM 输出必须标注"仅供参考，不构成法律意见"
- 数据不出境（中国客户）
- 涉密数据按等保 2.0 三级处理
- 大模型服务需信通院备案
