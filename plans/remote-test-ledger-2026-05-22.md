Remaining prompt work should focus on breadth and prompt quality, not baseline wiring.
- KG usefulness now has one targeted server proof that covers both graph search/diagnostics quality and explicit extractive chat answers on multi-hop questions. Remaining KG work should shift from “does graph help at all?” to broader question coverage and product presentation.
- Knowledge Base now has dedicated server proofs for mixed file-type corpus breadth, owner-scoped dataset boundaries, and outsider/viewer permission-sensitive filtering across dataset scope, group-based dataset sharing, and document-level ACL overrides. Remaining KB work should move to less common file families and more complex multi-group/document-sharing combinations instead of re-proving the same baseline trust boundaries.
- Browser UI now has three passing Playwright live proofs: business-surface smoke against the live backend, business-surface smoke against the deployed remote `web` page host, and a deeper live-stack workflow that exercises upload/parse/viewer/chat/command-menu on the deployed page host. Remaining UI work should broaden journey coverage instead of re-proving deployment wiring or the same single-document path.
- The dedicated `remote-web` Playwright lane now passes (`web/playwright.remote-web.config.ts` + `pnpm e2e:live:remote-web`) after the history hydration guards and remote `web` container rebuild from `main@059028d9`. Keep this lane for future deployment regression checks.
- Cross-encoder cold start is no longer allowed to stall the only API process while HuggingFace weights download. `main@ca40dd49` bounds local reranker load waits via `RERANKER_LOCAL_LOAD_TIMEOUT_SEC=2.0`, letting live chat degrade to base retrieval order while the background load continues.
- `scripts/production_readiness_chain.py` is not portable on the remote host/container as-is: host lacks `python-docx`, API container lacks `requests`.
- Use `scripts/remote_api_chain_smoke.py` for dependency-light server checks until the full readiness script is made portable.
- KG scale is functionally passing for 12 synthetic documents. Next optimization is extraction density/latency tuning on larger real PDFs, not another small-doc smoke rerun.
- KG event density and usefulness need product discussion before changing defaults. The current 12-doc scale guard generated 12 events because each synthetic document contains one obvious incident; this proves the channel is bounded and stable, but not that the event budget is useful for real KG-assisted RAG. Later discussion should compare baseline RAG vs KG-assisted RAG on real questions before increasing extraction density.
- Qianfan OCR is passing with the online Baidu Qianfan `deepseek-ocr` path on the remote server. Keep `QIANFAN_OCR_PROMPT` empty for that endpoint unless retested; the wrapper selects a short OCR prompt because longer Markdown conversion prompts returned empty output in live probes.
- OLMOCR, Docling, and MagicPDF are functional but slow on the small 2-page smoke PDF. On the 144-page PDF, HTTP 200 alone is not enough: direct serial runs showed `olmocr` can complete in about 495s on a clean GPU, `paddle_vl` still fails after about 49 minutes, and `marker` still times out after about 7100s even when the earlier service-readiness bug is removed. `scripts/remote_pdf_parser_performance.py` and `scripts/remote_parser_service_matrix.py` now treat requested/resolved backend mismatch as a failure class.
- Follow-up on real parsed outputs: the same 144-page MagicPDF document (`f20f6207-f808-4bd9-a8ae-8c2d92455793`) persisted `670` chunks and about `816k` chars after ingestion, but chunk-preview strategy spread is very large on the raw PDF path (`langchain_recursive=1151`, `parent_child=3702`, `semantic_sentence=1272`, `markdown_hierarchy=6203`). This needs product selection rather than assuming one default fits all long PDFs.
- Follow-up on real KG density: a default LLM KG extraction probe on dataset `cd232ae7-609d-415f-a43a-cca768aee664` was still running after `250+` extraction batches and had not committed final graph stats inside the probe window. This is enough evidence that long-document KG extraction needs a tighter bounded policy before it can be treated as a default production path.
- Follow-up on the KG budget fix: after deploying `main@154af84`, the same 144-page PDF was re-run with `KG_EXTRACT_MAX_CHUNKS_PER_DOCUMENT=120` and `uniform` sampling. Server logs showed the extraction restarted at batch `1` and advanced through about batch `98` before moving into embedding/indexing work, instead of exploding past `250+` extraction batches. The bound is now effective, but the default low-cost LLM backend still appears too slow for a comfortable long-document default.
- Follow-up on the long-document backend route: after deploying `main@57f7c75`, the same 144-page PDF automatically switched to the heuristic KG extractor on the default path (no explicit backend override). The synchronous extract completed in `13.411s` with `event_count=120`, and final stats for dataset `cd232ae7-609d-415f-a43a-cca768aee664` reported `120 events / 1148 entities / 1887 links`. This is the first server-side evidence that the long-document KG default is now both bounded and operationally fast enough to be usable.
- Follow-up on graph usefulness: in the first full real-PDF chain, `/api/v1/kg/search` returned status 200 but `0` returned clues for the generic question `"What is this paper about"`. The graph-enabled chat path still answered quickly by falling back to ordinary retrieval evidence. This means the long-document KG path is now fast enough operationally, but answer-quality lift from KG on generic summary questions is still unproven.
- Follow-up on permission realism: this deployment host still allows dev-style tenant bootstrap for previously unseen account ids, so outsider-deny verification has to pin a disposable account back to `viewer` before testing. That means the current permission matrix proves enforcement after role normalization, but not a strict “unknown account fails closed at the membership layer” production posture.
- The API container's default `python` is not the app virtualenv. For direct parser debugging inside `docker-mimirq-api-1`, use `/opt/venv/bin/python`; otherwise imports such as `langchain_core` will appear missing even though they exist in the app venv.
- Direct `magicpdf` inside the API container remains intentionally non-production and still should not be used as the deployment path. The validated production path is the standalone `mimirq-magicpdf` service image, which now also patches MagicPDF's internal `lang.ch` OCR model mapping to the shared `ch_PP-OCRv5_rec_infer.pth` cache layout when the older doc-recognition checkpoint is absent.
