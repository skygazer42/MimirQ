## 2 4 类流式场景

### 2.1 新闻 / 资讯

#### 痛点
- 新闻分钟级更新，传统批量入库延迟 1 小时 +
- 时效性强（"今天 X 公司发生了什么"）
- 跨源整合（路透 + 新华 + 财联社）

#### MimirQ 适用度：★★★（vertical 媒体客户少）

#### 客户：媒体平台 / 投研公司 / 政府舆情

### 2.2 金融行情 / 投研

#### 痛点
- 公告 / 调研报告分钟级更新
- 量化交易需要事件驱动 RAG
- 投研助手要"刚发的公告"

#### MimirQ 适用度：★★★★（金融 vertical 已是主战场）

#### 客户：基金 / 券商 / 量化 / 私募

#### 单项目预算：¥200-1000 万

### 2.3 IoT / 制造

#### 痛点
- 传感器数据流式产生
- 故障诊断需要实时关联
- 与制造业 KB 联动

#### MimirQ 适用度：★★（与现有文档 RAG 距离远）

#### 客户：工业互联网 / 制造业

### 2.4 客服 / 工单

#### 痛点
- 新工单实时进入
- 类似工单实时聚类 + 路由
- 客服坐席需要"最新案例"

#### MimirQ 适用度：★★★（已有部分支持）

#### 客户：客服 SaaS / 银行客服 / 电商客服

### 2.5 场景排序

| 场景 | 客户付费 | 技术契合 | 推荐 |
|---|---|---|---|
| 金融行情 / 投研 | ★★★★★ | ★★★★ | **优先** |
| 新闻 / 资讯 | ★★★ | ★★★ | 次优 |
| 客服 / 工单 | ★★★ | ★★★ | 次优 |
| IoT / 制造 | ★★ | ★★ | 不优先 |

## 3 实时 RAG 技术栈

### 3.1 4 层架构

```
┌─ 应用层（流式查询接口）─────────┐
├─ 实时检索层（HNSW 增量 + BM25）─┤
├─ 实时索引层（CDC + Stream）─────┤
└─ 数据源（Kafka / DB / API）─────┘
```

### 3.2 关键技术决策

| 维度 | 选项 |
|---|---|
| 数据接入 | Kafka / Pulsar / Kinesis / NATS |
| Stream framework | Flink / Spark Streaming / Kafka Streams |
| CDC 工具 | Debezium / Maxwell / Canal |
| 实时 vector | Milvus 实时 / Qdrant 实时 / Pinecone Streaming |
| 实时 BM25 | Elasticsearch 增量 / Tantivy 增量 |
| 失序处理 | watermark / event-time |

### 3.3 难点

- **延迟与一致性**：< 1s 延迟很难保证
- **资源消耗**：流式 = 全天 24h 消耗 vs 批量短时
- **failover**：节点宕机后数据完整性
- **回填**：错过的数据如何补
- **schema evolution**：新字段加入时不破坏

## 4 MimirQ 现状 + 落点

### 4.1 现状

- **批量入库**：当前主路径，定时调度
- **增量入库**：rag-ingestion-frontend 已规划，未真流式
- **Milvus 实时**：Milvus 2.X 支持 streaming，但 MimirQ 未启用
- **Kafka 集成**：无

### 4.2 4 个落点（如启动）

#### 落点 A：Kafka 接入

- `app/connectors/kafka_connector.py`（参考 base.py ABC）
- 配置驱动 topic + format（JSON / Avro / Protobuf）
- ~400 行 / 1 周

#### 落点 B：实时索引

- Milvus streaming 启用
- 实时 BM25 增量
- 实时 KG 抽取（轻量化）

- 与现有批量 orchestrator 共存
- 增量结果合并
- ~400 行 / 2 周

#### 落点 D：实时 UI

- 流式 chat 中"刚到的新内容"标记
- 实时数据流监控 dashboard

## 5 决策门槛

### 5.1 启动 P3-1 的硬门槛

| 条件 | 必须 |
|---|---|
| 客户 | 1 个金融投研 / 媒体客户付费 ≥ ¥200 万 |
| 场景明确 | "公告分钟级 RAG" / "新闻秒级 RAG" 这种具体需求 |
| 技术资源 | 至少 1 名 stream processing 专家 |
| 时间线 | 接受 3-6 月开发周期 |

### 5.2 不启动信号

- 客户只是"听说想了解"
- 现有批量入库 + 频繁触发已能满足（如每 5 分钟跑一次）
- 无金融 / 媒体客户
- 团队无 stream 经验

### 5.3 替代方案（90% 场景够用）

> 80% 客户对实时性要求其实是"分钟级"，**用现有架构 + 频繁调度**就够：
- 每 1-5 分钟触发一次入库
- 通过 cron + 增量入库
- 用户体验上几乎无差异

**仅当客户明确要求"秒级 < 5s"时才需真正流式 RAG。**

## 6 风险 + 范围之外

### 6.1 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 资源消耗 24h | 成本翻倍 | 仅高价值客户启用 |
| 故障恢复复杂 | 运维难 | 完整 SOP + 监控 |
| 数据漂移 | 检索质量下降 | 持续监控 + 重训练 |
| 与现有架构冲突 | 重构成本 | 新增不动旧 |
| 客户预期管理 | "为什么 1 秒延迟" | 明确 SLA |
| 流式 LLM 成本 | 每事件触发 LLM | 智能 batching + 缓存 |

### 6.2 范围之外（明确不做）

- 不做高频交易（< 1ms 不在 RAG 范畴）
- 不做实时翻译 / 实时字幕（独立赛道）
- 不做实时推荐（与推荐系统不同）
- 不做实时多模态（与视频 RAG 协同）
- 不做 IoT / 制造（与现有客户画像不符）
- 不做完全替代批量入库（共存）

### 6.3 不要的东西

- ❌ 不要在 90% 场景用流式（批量足够）
- ❌ 不要为了"实时"而实时（无客户价值）
- ❌ 不要单独投入 6 月开发（无客户）
- ❌ 不要"通用流式 RAG"产品化（按客户定制）
