# Agent Note: API 领域普通包与公共导入契约

Status: implemented

## Problem

schema 的领域目录已经改善导航，但命名空间目录没有明确的包入口，外部模块仍依赖内部文件位置；移动同一领域内的模型需要继续修改多个业务调用方。仅删除包标记或把文件放进子目录，没有建立用户要求的普通包与公开契约。

## Decision

app/api 父目录、schemas 九个领域和 api/utils 使用普通包，共新增十一处 __init__.py。schemas 根入口只说明领域边界，不全量聚合模型；base.py 保留共用 ORM 响应基类。各领域入口从实际定义模块显式导入有域外使用方的对象，用 __all__ 公开当前 418 个名称；公开对象仍是原类、类型或常量，没有包装、子类或动态查找。

域外消费者使用领域入口，域内继续直接依赖定义模块。151 个生产文件同步导入路径，局部名称、别名和所在作用域保持，类字段与业务体不变。领域内未来移动定义只需维护公共入口，调用方不需要知道内部文件布局。

utils 公共入口只发布公共文件与响应工具的九个名称；URL 与管线输入保留具名子模块。这样基础文件操作可独立导入，不加载应用配置和管线服务。app/api 父包不装配路由，不新增导入时任务或网络请求。

本决定更新[最初 schema 目录归类](2026-11-11-schema-domain-layout.md)中的包形式与域外导入规则；九域归类及两个实际模型合并的决定仍保留。它也更新[API 工具所有者](../simplification/2026-11-11-api-utils-owners.md)的包形式；工具实现、资源关闭与管线数据处理继续由原笔记持有。两篇均有仍在使用的独立理由，不归档。

## Alternatives considered

- 继续采用命名空间目录能避免入口文件和额外模型初始化，但域外仍依赖内部文件，缺少用户明确选择的普通包与公共契约。
- 只补包标记能让目录成为普通包，但没有解决域外导入分散、内部文件布局泄露的问题。
- 全部模型在 schemas 根入口导出，或把 URL／管线也放入 utils 根入口，能减少表面路径种类，却扩大初始化与配置依赖；当前只发布领域契约和无配置的公共工具。
- 动态懒加载可延迟个别模型依赖，但会增加属性转发和类型求值复杂度。当前初始化成本可见且不建立网络连接，采用显式导入。

## Consequences

调用方通过领域入口使用稳定对象，包标记与显式导出承担实际导入契约，源码文件数量不作为简化指标。公开名单需要随真实公共契约变动维护，内部模型不会因为位于目录中就自动公开。内部定义模块仍可正常解析，不创建旧路径兼容壳。

领域入口会更早加载其公开模型所需依赖。conversations 和 evaluation 可经 datasets 注册现有 ORM、构造已有 SQLAlchemy engine；源码与独立导入核对未建立连接。这个初始化取舍保留在记录中，不把领域包描述为零成本导入。普通 utils 工具入口保持配置隔离。

## Verification

202 个相关生产文件按 Python 3.11 解析与编译，Ruff 检查通过；190 个既有代码文件的非导入 AST 保持，schemas 根文件仅调整说明。151 个迁移文件的导入对象、别名与作用域核对保持。十一处新入口只包含说明、显式导入与 __all__ 声明。

十个公共包分别在新进程中独立导入，427 个公开对象与实际定义对象身份相同；连接调用设为拒绝，未发生连接。普通 utils 入口另在无导出模式下验证不加载应用配置与管线服务。修改前后完整 OpenAPI 相同，仍为 358 个路径、637 个 schema。独立只读审阅无新增待修项。

610 个测试文件哈希、共享 HEAD 和暂存区保持；Python 测试未新增、修改或运行。八个起点即存在的完整文件排版差异保留，194 个文件通过格式检查。全仓模块边界门禁有相对旧 CI 基线的 57 项差异，还原本批迁移前后发现身份和计数相同，增量为零，未重写基线。真实 HTTP、数据库事务和外部服务未执行。证据与具体限制见[验证记录](../../../../docs/maintenance/style-unification/verification.md)。
