# Agent Note: HTTP 中间件只处理实际请求职责

Status: implemented

## Problem

中间件目录保留已经没有调用的限流依赖、全局单例和配置入口。当前请求依赖已固定为本地单用户和单工作空间，中间件仍重复解码 JWT、从身份头派生日志身份和限流键。更换请求头可以得到新的限流桶，也会把未验证的身份写入日志。安全响应头逐项重复赋值和检查；响应头清理为固定规则维护了一套可选参数归一化流程。

## Decision

六个中间件继续承担各自明确的 HTTP 职责，配置值由主程序的 Settings 提供。构造函数只接收真实使用的参数，必须的配置明确必填，主程序直接传递已声明的值。请求体的零值仍明确表示关闭限制。

请求 ID 中间件只生成或验证请求 ID、绑定上下文、调用下游，并在 finally 恢复上下文。用户名与工作空间由现有请求依赖绑定。请求 ID 使用完整正则匹配，退出重复的字符检查和没有实际调用方的自定义表头参数。

限流按 ASGI 客户端地址选择桶，API 与聊天使用独立预算，保留预检、健康检查、文档图片路径的豁免。JWT 解码、身份头取值、未调用的限流依赖和全局单例退出。ASGI 允许客户端地址缺省，这类请求共用一个桶；它不是用户身份。限流算法、Redis 与内存实现继续由已有 core 模块持有。

安全响应头在构造时整理已启用的值，发送响应时使用框架的 setdefault 保留路由策略。显式空配置表示不追加对应安全头。指纹响应头固定删除四个实际字段，使用已核验的 MutableHeaders 删除协议，同时清理重复字段；缺少该字段时框架本身无需额外判断。

计时只保留实际使用的 Server-Timing 开关，固定的表头名和指标名直接出现在处理流程中。路由已有计时条目继续保留。请求体大小限制沿用已有的按块读取和框架 HTTP 异常处理，构造时必须明确提供上限。

实际调用在 `app/main.py` 中保持原注册顺序，四处不必要的配置回退退出。相关的共用限流与请求体错误处理决定见 [API 路由与输入归属](2026-11-10-api-route-and-input-owners.md)。

后续目录归并把三个本地请求依赖集中到 `app.api.dependencies`，把请求 ID 与计时集中到 `request_context.py`，把安全响应头与指纹清理集中到 `response_headers.py`。旧模块已删除，生产路由与 `main.py` 使用集中入口。限流和请求体限制继续独立，因为它们分别实现速率决策和 ASGI body 接收协议。

## Alternatives considered

- 保留 JWT 和身份头解析能够兼容原多用户模式，但它与当前已选的单用户依赖冲突，而且会使未验证的请求头影响限流和日志。
- 为响应头创建通用管理器可以集中处理各种未来策略，但实际只有明确的七个安全字段和四个删除字段。构造时整理值，响应时直接调用框架接口即可。
- 把全部中间件改成自写 ASGI 事件包装器可以统一外形，但会新增响应与上下文转发逻辑。现有 BaseHTTPMiddleware 协议和按块接收边界分别保留。

## Consequences

目录七个文件由 541 行变为 278 行，本轮减少 263 行；六个中间件均已逐项核对。只保留真实协议允许缺省的判断，包括请求 ID、Content-Length 和 ASGI 客户端地址。该目录不再通过任意身份头提供多用户限流，独立认证及其他业务模块不在本次改写范围内。

## Verification

两个回归先确认原实现会接受伪造日志身份，并通过变化身份头得到新限流桶，调整后符合预期。44 项请求上下文、响应头、计时、限流和相关检查通过；请求体限制的 14 项相关检查通过。组合测试按真实注册顺序覆盖全部六个中间件和 CORS，确认 413／429、请求 ID、安全头和计时信息共同保留。另验证上下文并发隔离、异常恢复、缺省客户端地址，以及 Server-Timing 关闭值和已有路由策略。

六处主程序中间件注册参数与实际构造签名核对通过，目录通过 Python 3.11 语法解析。请求 ID 模块可独立导入，不加载 Settings、JWT 或数据库。检查使用隔离测试配置，没有启动数据库、模型或生命周期任务。

目录外另有两项验证限制：完整主程序导入被 RAG 中的 `app.config.rerank_profile` 残留引用阻断；同一网络测试文件中的三项 URL 检查在当前未提交的 URL 实现上遇到 `str.is_global` 属性错误。本次没有修改这些目录外实现，完整应用启动尚未验证。
