# Agent Note: 前端显式刷新与请求结果归属

Status: implemented

## Problem

用户点击文档或导入任务的刷新按钮时，原 fetchQuery 会复用仍在新鲜期的缓存。浏览器中把任务接口切换为失败后，刷新既没有请求，也没有错误提示，用户无法确认服务当前状态。

导航把管理员健康详情当成公共就绪状态；普通用户无法用这个受限接口判断服务是否就绪。任务读取失败与空集合混在一起；图谱服务把失败转换为空图，切换范围与并发展开的结果还需要各自持有发布权。

## Decision

文档与导入任务的显式读取在已有 fetchQuery 参数中使用 staleTime: 0。普通订阅查询仍使用 QueryProvider 的缓存配置。动作完成只更新发起时的查询，不切换当前列表；查询实体、身份清理与轮询归属仍沿用已有实现。

公共可用性由 /health/ready 提供；健康详情继续由 /health/details 提供，导航只有获得 observability.read 时才请求并消费详情，包括已有缓存。React Query 的 signal 沿现有客户端传递，不另建取消控制器。

任务错误作为查询结果的一部分传给已有 Alert，刷新失败时保留缓存行和动作。图谱加载和展开把当前错误交给现有反馈层；范围变化清除旧范围内容，当前范围刷新失败则保留可用图谱。图谱加载与展开分别拥有忙碌事实，由页面组合显示，并发展开全部结束后才解除展开状态。

审计删除结果与分页游标在外部响应边界通过现有 Zod 校验。缺失的删除计数或无效游标抛出带上下文的错误，不转换成零或导出结束；真正的空结果和零计数仍有效。

## Alternatives considered

- 保留 fetchQuery 的新鲜度策略，能减少短时间内的重复 GET，也是旧决定的取舍。但显式刷新承担确认当前结果的职责，浏览器已复现其不发请求的问题，因此仅这些明确读取入口使用 staleTime: 0。
- 合并公共就绪与健康详情查询能减少一条读取路径，但两者的访问权限和响应合同不同。保留两项真实职责，已有同权限的详情消费者继续共享缓存。
- 为每个健康与任务 Hook 创建 AbortController，取消意图直观，但会重复 React Query 已有的资源所有权。直接转发框架信号即可；图谱局部操作仍按实际范围检查迟到结果。
- 刷新失败时只显示错误，渲染分支简单，但会隐藏仍可用的缓存任务与动作。错误提示与缓存内容并存，初次失败也不会显示成功空列表。

## Consequences

显式刷新会增加一次实际 GET；相同查询的并发请求仍由 React Query 合并。消费 signal 后，失效读取会按框架合同取消和回退状态；已提交的服务端动作不因此回滚。保留真实可选字段，包括批量上传响应中的可选数组，不把接口未保证的字段强制为必填。

已退休的 Legacy 导出别名没有调用方，实际公共入口仍存在。本次没有引入新依赖、状态容器或目录框架，也不代表已经逐函数完成整个前端的规范审查。

浏览器验证使用生产前端与隔离接口响应，覆盖公共就绪、无权限时不请求详情，以及键盘刷新失败后缓存任务仍可用；不代表真实后端集成已通过。最终静态、类型、单元、构建及规则证据结果见 .frontend-structure/20261112-frontend-guidelines/task.md 与同目录记录。哈希核验只说明来源与代码快照对应，不能证明业务语义。
