# Agent Note: 评测主请求错误的已知凭证脱敏

Status: implemented

## Problem

Dify 三路评测承诺不把 API key 写进产物，但常规主请求的两处错误分支直接保存 `str(exc)[:1200]`。HTTP 错误正文是外部文本，若正文回显本次请求已知的 key 或 token，这段文本会进入结果条目，继而进入增量检查点、最终 run 文件和归档。Dify 结构化诊断也会再次消费同一错误文本。

现有 `_safe_error` 已在预检和回填错误中处理已知凭证，常规 Dify 与直连 MimirQ 的主请求没有使用它。源码路径构成可达反例；本次没有观察或执行真实泄漏场景。

## Decision

`scripts/dify_3way_benchmark.py` 的 Dify 主请求错误把 `str(exc)` 交给现有 `_safe_error`，只提供该请求的 `app.api_key`；直连 MimirQ 分支只提供自己的 `token`。Dify 的 `error` 字段与 `diagnose_dify_error` 继续使用同一个局部变量，结构化诊断只读取已脱敏文本。

原 helper 的完整签名、函数体、文本规范化、截断和替换次序保持。请求、重试、HTTP 与 `ok` 状态、诊断字段结构、结果排序、检查点和产物写入链保持；不增加配置、通用凭证收集器、扫描框架、异常吞咽或默认成功路径。

## Alternatives considered

在所有产物写入器里递归替换能够集中处理输出，但写入器缺少本次请求的凭证归属，还会扩大到答案、证据和缓存数据。现有错误分支已经持有准确的请求凭证，可以直接复用既有规则。

删除错误文本能避免原文进入产物，却同时丢失 HTTP 信息与 Dify 诊断所需内容。已有 helper 保留诊断文本，只按原策略替换显式传入的已知凭证。

## Consequences

常规主请求的已知完整凭证文本先经原规则处理，再进入原有持久化消费者。非敏感错误的正常控制保留原值；本次不扩展 helper 对编码、截断边界或其他请求凭证的处理策略。

固定 Git 源码、原 helper 与七组合成文本在修改前冻结。完整模块 AST 只允许两处明确表达式投影，其他函数、签名、helper 全文和数据流保持。标准库原生文本与 JSON 数据证据覆盖假 key、直连 token、重复出现、普通错误和空凭证控制；主请求、诊断、增量与最终写入消费者分别核对。

验证不调用原 helper、异常、请求、生成器、回调或业务函数，不读取实际 key、env 或业务数据，不新增、扩写或执行 Python 测试。未启动服务、浏览器、网络或 SDK／模型／数据库。证据说明源码可达反例及其定点修复，不代表观测到真实泄漏或完成运行验收。

活跃笔记按 `_safe_error`、评测产物和错误脱敏检索，没有相同决定。[诊断与回放脚本的内部记录](../simplification/2026-11-05-evidence-replay-cli-owned-values.md)持有其他工具的既有脱敏与输出边界；设置区状态记录针对不同对象。本篇不替代或修改这些决定。
