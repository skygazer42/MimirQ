# Agent Note: 本地预览完整解析后替换原记录

Status: implemented

## Problem

本地预览的库 ID 不对应服务器 workspace 文档，直接用于解析或编辑接口会请求不存在的对象。上传再解析会产生新的服务器 ID，若提前新增库条目或提前改写原记录，就会出现重复条目、失败改变原记录或丢失旧正文可见性。

上传和解析期间，用户还可以切换文档、删除目标目录或重新登录。仅检查一次 loading 或在取消查询后才检查会话，无法保证结果仍属于当前操作。

## Decision

用户确认成功后用完整解析结果替换本地记录，只保留一个条目；失败保留原记录。完整上传、解析与内容合同继续由 parsingApi 持有。本地预览的显式保存使用 Store 已有 requirePersistence 能力，成功文案反映实际保存位置。

新的服务器记录只在完整解析成功后接管本地索引。Store 单次替换保留原记录当前目录和工作流信息，去除已被目录同步发现的同一新 ID；索引写入失败恢复原集合。Store 继续拥有缓存更新、在途写入取消和旧缓存清理。

失败撤销临时服务器文档，取消该会话尚未完成的目录查询，清除临时本地条目后再刷新真实目录。每次等待后先检查会话归属，再操作当前 QueryClient；清理失败明确反馈。服务器与浏览器不组成跨系统事务，关闭浏览器或切换身份后不会越过新身份继续执行旧凭据的清理。

普通、目录和 ZIP 文件共用局部队列构造，目录查找消费 Store 当前集合。目标目录被移除时取消该上传，避免失效目录 ID 使新文档不可访问。上传完成保留用户期间的新选择。已保存正文与新任务状态分开呈现，失败和处理中仍可查看旧结果。

## Alternatives considered

- 使用无状态 preview 可以避免新建服务器文档，但实际接口只返回片段及分析，不提供 workspace 完整正文/原文和元素合同，且清理临时图片资源；不能用它降低完整解析能力。
- 上传后立即替换 ID 可以让重试直接复用服务器对象，但会在解析失败前改写原本地记录，与用户要求的成功替换时序不一致。
- 用新增与删除两个独立库动作实现替换，复用量更大，但索引写入失败会留下中间状态；由实际 Store 持有一次替换与失败回滚。

## Consequences

成功后文件身份、当前目录和完整内容连续，失败保留可读旧正文和真实错误。代价是新增服务器对象需要失败撤销；撤销失败不能假装已经回滚，用户会看到明确提示，真实目录继续提供处理入口。浏览器异常关闭与远端操作无法组成原子事务。

139 项最终定向、完整 verify 的 198 文件/1,480 项与两条后补会话回归通过，相关最终 lint/类型检查通过。Edge 桌面和手机完成本地保存、失败保留、键盘重试、单条替换及刷新读回，原生缓存真实，HTTP 为 fixture。详细写法、命名和检查记录在 .frontend-structure/20261112-full-frontend-guidelines/parsing-actions/；全前端目标仍在进行。
