# Agent Note: 原文件恢复按文档拥有并保留保存正文

Status: implemented

## Problem

源关联等待缓存后没有核对会话；同一文档的两次恢复乱序完成时，旧 File 会替换新 File。恢复还会把本地预览文件元数据写进远端文档，界面却声称已替换服务器源；实际后端没有这项接口。

workspace 错误/待解析/中断记录跳过保存正文，刷新恢复后只剩空队列结果。自动恢复把缓存错误算成 miss，并按“文件夹已恢复”阻止后续候选。源缓存延迟 open 也没有同记录的删除/新写拥有者。

## Decision

本地原文件关联负责预览；远端重新解析使用服务器已保存的源，名称/格式/大小继续属于真实服务器文档。本地预览成功转完整结果后替换原记录的用户选择保持。

源请求从入口按库 ID 持有 controller，缓存和 mount 沿同一拥有者推进；后来的恢复、会话变化或卸载使旧结果失效。恢复所有任务状态时都调用现有内容加载器，分别保留任务错误与可选保存正文。独立目录移动使用当前库事实，不重建已有队列的历史运行。

自动恢复观察真实候选身份与资格，自身写入正文不重启整批工作；尝试按文档记录，读取错误和真正 miss 分开。StrictMode 清理释放当前未完成标记，旧 await 不清后一次标记。并行库读取恢复相同一对正文允许继续，不同新编辑仍拒绝旧恢复；同库 ID 的原文件到达后衔接当前选择。源写事务由缓存层按 scopedId 持有 controller，新写/删除取消旧事务，调用方 signal 转接且 finally 移除监听。真实 File 空字段和 0 不改成默认名称、MIME 或时刻。

## Alternatives considered

- 只在 mount 最后核对账号，新增代码少，但同账号同文档的新旧请求仍会覆盖，且旧缓存写入可能已提交；拥有者必须从关联/恢复入口延续到写事务。
- 继续把本地 File 元数据写进远端条目，界面可以显示刚选文件，但后端解析的仍是旧源，记录和结果会指向不同文件；明确保留本地预览语义，不伪造源替换功能。
- 仅在 parsed 状态恢复正文，分支简单，但失败任务可以有完整旧正文；统一读取内容，真实状态与内容分开。

## Consequences

用户新选择、当前目录、服务器身份和旧正文保持连续；缓存失败可见，源删除不会被当前模块的旧事务重建。代价是恢复意图和缓存写事务各自需要一个实际资源拥有者，分别履行卸载/同键删除责任；没有增加另一份持久化文档状态或重试协议。
