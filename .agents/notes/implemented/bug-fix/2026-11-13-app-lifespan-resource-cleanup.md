# Agent Note: 应用退出由一个清理栈持有资源

Status: implemented

## Problem

FastAPI lifespan 的 yield 后顺序关闭只覆盖正常退出。请求服务阶段的异常、取消，或前一个关闭动作失败，都可能使后续全局资源没有机会释放。启动已经创建部分资源后失败，也需要同一退出责任。

## Decision

`app/main.py` 使用标准库 AsyncExitStack 注册现有全局资源的关闭动作。执行顺序固定为 HTTP 客户端、队列观测任务、队列连接、数据库引擎、OpenTelemetry。注册在启动前完成，因为这些实际关闭函数支持尚未初始化的状态；启动步骤及同步／异步调用方式保持。

栈在成功、启动失败、服务阶段异常及取消时尝试每个独立关闭动作。异常遵循 AsyncExitStack 的传播和上下文规则，关闭失败不转成成功；这不保证已被中断的单个关闭动作完成，也不提供反复取消的硬时限。后台预热任务继续由其实际服务持有，本决定没有新增停止 API 或完整任务组。

## Alternatives considered

直接在 yield 外加 try/finally 能覆盖服务阶段失败，但 finally 内第一个失败仍会跳过其他资源。手写多层 finally 可以保证尝试每个动作，但会把标准库已有的异常处理顺序重复在应用入口。退出栈集中持有这个顺序，关闭细节仍在原有模块。

把数据库或分词器初始化移入线程可以减少事件循环阻塞，但会改变 SQLite 连接和进程初始化行为，故当前只统一释放责任，不改变启动执行位置。

## Consequences

入口只维护一份资源释放顺序；HTTP 关闭成功日志在整段退出栈正常结束后记录。后续新增全局资源必须检查未初始化关闭和实际生命周期，不能只往正常 yield 后追加语句。数据库依赖自身的事务／rollback／close 策略仍按[公开数据库所有者](../simplification/2026-11-13-database-public-owner.md)保留。

纯 AST 和假资源探针对照正常顺序，覆盖十个启动位置失败、服务异常／取消、五个关闭位置普通与控制异常、Session 关闭和 CORS 展开。没有启动真实 lifespan、数据库、队列、分词器或外部服务；离线轨迹不能替代部署后的服务停止验证。
