# Agent Note: 活动版本过滤失败终止本次检索

Status: implemented

## Problem

普通 RAG 引擎和 LangGraph 都通过数据库读取文档的活动处理版本，再加入 `doc_pipeline_key` 过滤。两处捕获整个查询与组装流程的所有异常，记录 debug 后返回原过滤器。数据库故障或错误 metadata 因此会撤掉活动版本限制，让请求继续读取其他版本的 chunks，却没有明确失败响应。

## Decision

两条入口都直接传播活动版本查询和过滤组装异常，由原请求或任务错误入口处理。租户与文档谓词、ready 判定、活动／历史 hash 优先级和 `doc_pipeline_key` 集合构造保持。真正没有 Session、租户或文档范围时仍直接返回原过滤器；查询成功但没有可用活动键时继续遵循原无版本记录规则。

两份相同规则由 `app.rag.core.pipeline_scope.apply_active_pipeline_metadata_filter` 持有。LangGraph 以原私有名直接导入，RAGEngine 的原调用名静态绑定到同一模块函数；流式准备阶段的调用和既有替换入口保持。新模块在加载时仅依赖标准库，文档模型和 hash 所有者仍在原分支中延迟导入，不创建 Session 或增加框架对象。

该过滤只限制处理版本，不能代替既有的租户、文档权限或 dataset 过滤。原有用户 metadata 条件继续保留在新建的过滤器字典中；不修改调用方传入的字典，不通过空过滤器、缓存或其他存储替代失败查询。

## Alternatives considered

- 失败后继续返回原过滤器能提高表面可用性，但把查询故障变成版本范围扩大，返回的内容不再满足原请求的活动版本语义。
- 失败时返回空结果可以避免读取旧版本，但仍把数据库故障表示成成功的零命中，调用方无法区分无证据和过滤不可用。

## Consequences

无法确定活动版本时请求失败，避免以另一组版本继续作答。以前依赖静默绕过的请求需要先修复数据库或 metadata；真实缺少版本信息的历史记录仍按既有规则处理，本次不增加数据迁移或统一拒绝旧记录。

验证限定于 Ruff check/format、Python 3.11 AST 与源码编译、完整模块结构对照、调用方和 Note 门禁。结构对照仅允许两处外层异常包装退出，原查询与组装语句保持相同。按用户要求不新增或运行 Python 测试，不执行数据库、检索、向量存储或模型调用。

共享增量对照原图函数与引擎方法的完整函数体、参数和模块 AST：仅允许同一规则移入实际 owner、引擎实例名消除和静态绑定、图模块直接导入；查询条件、返回字典和延迟导入时点保持。
