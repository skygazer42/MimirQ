# Agent Note: 切块自动调参的零分候选排序

Status: implemented

## Problem

`chunk_autotune` 的评分约定是越低越好，所有目标都满足时会产生合法零分。旧排序键使用 `score or 9_999_999`，把零分与缺失分数混在一起，导致分数为 100 的候选排在零分之前。主流程取排序后的第一项生成 preset，因此会把较差策略作为推荐导出。

## Decision

现有排序函数只在分数缺失或为 None 时使用原整数哨兵，其余分数仍经原 int 转换。合法零分按零排序。HTTP 失败分支继续产生 9_999_999，非零分数、候选字符串第二排序键、平分顺序、排名编号与候选预算保持。

本修复独立于同批脚本风格调整。原评分、两个候选结果生产分支、排序调用、第一项选优与 preset 输出链保持；后续纯风格比较使用本修复后的切块脚本快照，不把排序变化混入表达式简化。

## Verification

固定 Git 整模块 AST 只允许排序键的分数表达式变化，其他函数体、声明、默认值和模块初始化保持。验证同时记录评分越低越好、成功分支的实际评分、HTTP 失败哨兵，以及排序到第一项输出的真实来源。原生字面量元组比较覆盖零分、100、哨兵和相同分数的候选字符串顺序；不调用评分函数或排序键函数，不抽取并执行业务代码。

## Alternatives considered

- 保留 `or` 哨兵可以继续容忍假值，但合法零分正是假值，会继续输出错误推荐，因此改为显式区分 None。
- 只使用 `row.get("score", 9_999_999)` 能保留零分与缺失默认值，但显式 None 会进入 int 转换并改变原缺失处理，因此同时保留 None 的哨兵语义。

## Consequences

满足全部目标的零分候选可以排在正分候选之前。现有整数分数生产契约、失败哨兵与并列规则仍是维护排序的依据。若评分量纲或失败结果结构改变，需要同时核对评分生产者与第一项选优；本修复没有增加配置、补丁映射、排序器或默认成功状态。

活跃笔记检索中的切块质量建议所有者记录讨论另一个已退休服务，混合检索排名和表关系记录属于其他排名系统，与此 CLI 无重叠决定，均保留。验证仅使用隔离 Python 3.11 标准库源码 AST、哈希、JSON 与原生字面量元组，以及 Ruff 和笔记静态门禁；不运行目标脚本、SDK、模型、数据库、业务数据、业务正则或 Python 测试。
