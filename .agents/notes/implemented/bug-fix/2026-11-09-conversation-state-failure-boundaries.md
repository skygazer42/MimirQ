# Agent Note: 对话范围与后台状态保留真实失败

Status: implemented

## Problem

对话访问检查把全部已删除的文档 ID 提交为空数组，聊天范围解析随后把它当作开放／数据集范围。解析器本来有“文档已不可用，重新选择范围”的 409，但访问检查提前清空 ID，使该分支无法保留原始选择意图。

## Decision

仅在至少有一个文档仍存在时，访问检查才按原规则清理部分缺失 ID 并提交。全部缺失时保留原明确文档范围，不把它持久化成空数组；后续聊天解析继续使用已有 409。历史记录等访问者仍沿原返回协议取得可读列表，不新设标志、状态表或请求字段。

所有者优先级、旧 user_id 兼容、数据集和文档 ACL、部分权限的筛选、部分缺失的更新时间保护／commit／refresh 保持。用户明确选择新文档或数据集的入口继续先于旧范围解析处理，主动清除范围仍由原明确编辑操作持有。

## Alternatives considered

- 继续清空全部缺失 ID 能清理旧引用，但会把原先受限的查询变成另一个范围，且重试无法知道先前范围已失效。
- 新增 expired 状态可以单独表达失效，但需要迁移、写入和接口协议；保留已有非空 ID 即可让现有解析器处理。
- 在访问检查对全部缺失直接抛 409 可以立即失败，但会连带阻止原本允许的历史读取，因此只保留选择意图，由聊天范围入口判断是否能发起检索。

## Consequences

全部失效的范围会要求用户重新选择，不能无声扩大检索。旧 UUID 会保留到明确编辑操作，使用者需要区分明确未设范围和已有范围已失效；部分失效仍按原规则清理。

既有[聊天类型与实际所有者](../simplification/2026-11-03-chat-runtime-typed-contracts.md)继续持有输入和转发归属，本篇持有范围失效与后台失败的行为约定；早期正常路径静态证据不替代本篇错误政策。

核对真实 Conversation 模型、加载／访问／范围解析顺序、现有 409 与明确范围覆盖分支。完整模块 AST 对照仅允许清理条件及其说明改变，所有 SQL、权限和正常返回保持；限定 Ruff／格式、Python 3.11 AST／源码编译与 Note 门禁提供静态证据。按用户要求未新增、修改或运行 Python 测试，未执行范围解析、检索、历史读取、SQL 或请求，静态证据不证明端到端表现。
